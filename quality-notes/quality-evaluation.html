▸ 核心要点
1质量属性 — 开发期 vs 运行期
开发期质量属性（6个）
  • 易理解性：设计被开发人员理解的难易
  • 可扩展性：适应新需求增加新功能的能力
  • 可重用性：重用系统或其部分的难易
  • 可测试性：测试满足需求规范的难易
  • 可维护性：修改缺陷、增加功能的难易
  • 可移植性：迁移运行环境的难易
→
运行期质量属性（7个）
  • 性能：及时响应能力（速度、吞吐量）
  • 安全性：阻止非授权使用的能力
  • 可伸缩性：用户增加时维持服务质量
  • 互操作性：与其他系统交换数据的能力
  • 可靠性：持续无故障运行的能力
  • 可用性：正常工作的时间比例
  • 鲁棒性：非正常情况下的容错能力
2架构评估的 9 大质量属性 + 设计策略
属性核心定义关键设计策略
性能 响应时间、吞吐量 优先级队列、增加资源、并发机制、资源调度
可靠性 一段时间内正常运行不故障（MTTF/MTBF/MTTR） 心跳、Ping/Echo、冗余、选举
可用性 需要时可使用的时间比例 心跳、冗余切换、状态同步（检查点/回滚）
安全性 机密性、完整性、不可抵赖性、可控性 入侵检测、身份认证、访问控制、追踪审计
可修改性 以高性价比快速对系统变更 接口-实现分离、抽象、信息隐藏、松耦合
功能性 系统完成预期工作的能力，多构件协作 接口标准化（OpenAPI）、服务编排
可变性 架构适应未来变更、支持产品线演进 配置驱动（Feature Toggle）、抽象核心逻辑
互操作性 与其他系统交换数据或调用服务 协议兼容（REST/gRPC）、数据格式统一
易用性 用户界面和交互设计，学习曲线 用户体验优化、交互流程简化
2.1可靠性 vs 可用性 — 易混淆区别
R
可靠性 Reliability
  • 强调不故障
  • 指标：MTTF/MTBF/MTTR
  • 例：Provider A 全年零故障 → 高可靠性
A
可用性 Availability
  • 强调故障后快速恢复
  • 指标：可操作时间比例
  • 例：Provider B 停机5小时但快速恢复 → 高可用性
3质量属性场景 — 6 要素描述法

质量属性场景 = 一种通用的 非功能需求描述方式，由 6 部分组成：

刺激源
谁（人/系统/传感器）
刺激
做什么（事件/请求）
环境
什么条件下发生
制品
影响系统的哪个部分
响应
系统如何应对
响应度量
如何量化衡量

可修改性场景示例

刺激源：开发人员 → 刺激：修改功能 → 环境：设计时 → 制品：UI层 → 响应：定位修改点、不影响其他功能 → 响应度量：修改影响的元素数量、成本

4系统架构评估 — 核心概念
S
敏感点
  • 对单一质量属性敏感的特性
  • 调整后某质量属性显著变化
  • 例：缓存大小 → 影响性能
T
权衡点
  • 影响多个质量属性的特性
  • 多质量属性此消彼长
  • 例：加密级别↑ → 安全性↑ 性能↓
R
风险点
  • 潜在隐患、不确定性
  • 可能导致需求不达标
  • 例：新技术选型无验证
N
非风险点
  • 设计成熟、低不确定性
  • 技术验证充分、符合标准
  • 例：成熟框架的标准用法
5三种架构评估方式
方式核心方法要求示例
调查问卷（检查表） 向开发团队发架构问卷，收集主观反馈 评估人员了解领域和架构 "当前系统性能是否满足需求？"
基于度量 定量指标（代码行数、响应时间、内存） 评估人员了解技术细节和度量标准 测量查询平均响应时间、吞吐量
基于场景（主要方法） 定义场景，模拟测试质量属性满足程度 评估人员既熟悉领域也熟悉架构 "1000用户同时观看高清视频"
6三大架构评估方法
1
SAAM — 软件架构分析方法
  • 英文：Software Architecture Analysis Method / 最早的方法，Rick Kazman 等，约 1994
  • 主评质量属性：可修改性
  • 5步：场景开发→架构描述→单个场景评估→场景交互→总体评估
  • 何时用：架构最早期，方案尚不成熟时快速筛查，也可比较候选方案
2
ATAM — 架构权衡分析方法
  • 英文：Architecture Tradeoff Analysis Method / SEI 在 SAAM 基础上改进，约 1998
  • 评估性能/可用性/安全性/可修改性的折中
  • 核心产出：质量属性效用树；识别风险/敏感点/权衡点
  • 何时用：架构中期，初步成型需多属性权衡时
3
CBAM — 成本效益分析方法
  • 英文：Cost Benefit Analysis Method / Barry Boehm 等；ATAM 的经济延伸
  • 核心依据：投资回报率（ROI），选 ROI 最高的策略
  • 何时用：架构后期/决策期，在多个可行方案中按性价比拍板
对比
三者关系
  • SAAM：最早最通用 → 可修改性
  • ATAM：多质量属性权衡 → 效用树
  • CBAM：ATAM 补充 → 成本效益 = ROI
6.1演进历史 & 何时使用
方法中文全称关注点适用阶段
SAAM 软件架构（体系结构）分析方法 单个质量属性（可修改性），基于场景定性分析 早期草稿期 · 比较候选方案 · 成本低
ATAM 架构权衡分析方法 多属性权衡（性能/可用/安全/可修改），效用树排序，找敏感/权衡/风险点 中期架构成型 · 需多种冲突质量目标取舍
CBAM 成本效益（成本收益）分析方法 在 ATAM 基础上加经济量化（ROI），选最划算的架构策略 后期决策 · 多个可行方案中挑性价比最高
◆ 怎么记住 + 什么时候用

一条线串起来：SAAM 看"好不好改"（单属性·早期）→ ATAM 看"怎么取舍"（多属性·中期）→ CBAM 看"值不值"（算 ROI·后期）。三者层层递进，不是三选一。通俗理解：最小的是问你"这房子隔断好改吗"（SAAM），中等的是"好用、好改、安全、不垮之间要东墙补西墙怎么办"（ATAM），最大的是"这么多取舍到底花钱值不值"（CBAM）。在写大量代码前做——拿具体质量场景当"考卷"，提前暴露风险和权衡点，避免地基没打好就开盖。

7ATAM 四阶段详解
阶段目标关键活动
1. 描述和介绍 定义评估范围、目标、要优化的质量属性 收集架构文档，与干系人确定评估目标
2. 调查和分析 分析架构对质量属性的影响，识别问题与权衡 生成质量属性效用树，按"对成功的重要性"和"架构师角度难易程度"两个维度排序
3. 测试 验证架构是否满足质量属性需求 场景分级、投票、分析不同架构方法的影响
4. 报告 总结评估结果，提供改进建议 生成评估报告：发现、性能数据、改进建议、权衡决策
7.1质量属性效用树（Utility Tree）

高频考点：效用树是 ATAM 第二阶段（调查和分析）的核心产出，用来对质量属性进行分类和优先级排序。一句话：把模糊的大目标拆成可量化、可排序的小场景。

层
树根 → 质量属性 → 属性分类 → 质量属性场景（叶子）
  • 树根：系统的总体"效用"/大目标
  • 第2层 质量属性：性能、可用性、安全性、可修改性（ATAM 只关注这 4 类）
  • 第3层 属性分类：对某个属性进一步细化（如性能→响应时间/吞吐量）
  • 叶子 质量属性场景：具体、可测量的场景（刺激→环境→响应）
例
在线支付系统示例
  • 根：系统效用
  • 质量属性：安全性 → 属性分类：访问控制 → 场景：用户登录需双因素认证，未授权访问率 <0.1%
  • 质量属性：性能 → 属性分类：响应时间 → 场景：高峰用户单击支付，页面 2 秒内返回

三个易混概念

  • 效用树 = 结构化"组织框架"（根→属性→分类→场景），作用是梳理 + 排序。
  • 质量属性场景 = 标准化"描述单元"（刺激-环境-响应），作用是无歧义定义需求。
  • 质量属性分类 = 静态"知识体系"（运行期/开发期），作用是提供基础清单。

每步做什么 —— 以"在线支付"为例

步骤动作例
① 树根确认整体目标（到底要什么"好"）系统在高峰也能稳定、安全、快速完成支付
② 质量属性从经典清单挑本项目最相关的大类性能、安全性、可用性、可修改性
③ 属性分类把每个属性细化成技术、可测量的维度性能→响应时间/吞吐量；安全→访问控制/审计
④ 场景（叶）用"刺激→环境→响应"写成具体、可量化的小目标高峰用户点击支付，页面 2 秒内返回；登录需双因素认证、未授权率 <0.1%
⑤ 修剪砍掉不重要/过时场景，保留核心（≤50）只留影响成败的场景
⑥ 优先级对每个叶子打"重要度 × 难易度"（H/M/L）(H,L) 重要且易实现 → 最优先
⑦ 用起来找高风险、敏感点/权衡点，选对应质量属性战术解决高并发场景 → 用优先级队列、增加资源等性能战术

一句话记住"怎么形成"

先定整体目标（根）→ 拆成几个质量属性 → 每个属性再细化成可测维度 → 落到具体场景 → 剪枝保留重点 → 给每个场景打重要度×难易度。核心就是自顶向下拆 + 由下往上排，把"系统要好"从一句话变成一张可执行的问题清单。

修剪与优先级排序（考点）

初始树很大，先修剪保留重要场景（通常 不超过 50 个），再对每个场景打两个维度（都用 H/M/L 表示）：

  • 重要度（Importance）：该场景对系统成功的重要性（干系人判断）。
  • 难易度（Difficulty）：该场景实现的难易程度。
  • 例：(H, L) = 重要且易实现，最优先处理。
◆ 效用树怎么理解

效用树就是把"系统要好"这句话，像剥洋葱一样剥下去：第一层问"好在哪些方面？"（性能/安全/可用/可修改）；第二层问"每个方面具体指什么？"（性能分响应时间、吞吐量）；最底层落到"能测量的场景"（高峰 2 秒内返回）。然后给每个叶子标"重不重要 + 好不好做"（H/M/L），就能看出先解决哪个了。它就是 ATAM 的"问题清单"，先发现问题，再用质量属性战术去解决问题。

▸ 总结

以6要素质量属性场景描述非功能需求，通过识别敏感点→权衡点→风险点锁定架构关键决策，再用SAAM（可修改性）→ ATAM（多属性权衡+效用树）→ CBAM（ROI选最优）三种方法逐级递进评估——确保架构在编码前就经得起检验。
