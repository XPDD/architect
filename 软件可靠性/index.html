01

基本概念与定量描述

▸ 定义

软件可靠性是软件产品在规定的条件和规定的时间区间内完成规定功能的能力。

可用性（Availability）—— "能不能用"
  • 正常工作时间所占比例（某个时刻系统在不在线）
  • 核心指标：可用度百分比（如 99.9%，"几个 9"）
  • 提升手段：冗余、负载均衡、故障转移、快速恢复（治"坏得快"）
  • 像随时待命的服务生——中间离开过没关系，你需要时"在场"就行
可靠性（Reliability）—— "做得好不好"
  • 持续无故障运行的能力（一段时间内正确、稳定）
  • 核心指标：MTBF / MTTF（平均无故障时间、失效前时间）
  • 提升手段：代码质量、充分测试、容错设计、失效预防（治"老出错"）
  • 像从不出错的马拉松选手——任务从头到尾一次做对、不中断
关系与易混可用性 = MTTF / (MTTF + MTTR)。可用性看"能用的时间占比"，可靠性看"少出错、不出错"。

▸ 一句话记忆 + 两个反例（考点）

口诀：卖门票的看"能用"（可用性），管账本的看"别算错"（可靠性）。

  • 高可用、低可靠：网页随时打得开（可用），但一提交表单就报错（可靠低）。
  • 高可靠、低可用：系统运行极稳定（可靠），但一升级维护就停机半天（可用低）。

→ 金融/支付/航天/工业：重可靠；在线电商/社交/视频：重可用。

▸ 软件 vs 硬件可靠性（4 点差异，考点）

  • 复杂性：软件复杂性比硬件高，大部分失效来自软件失效。
  • 物理退化：硬件失效主要是物理退化所致，软件不存在物理退化。
  • 唯一性：软件是唯一的（同版本每个 copy 相同），两个硬件不可能完全一样。
  • 版本更新周期：硬件较慢，软件较快。

▸ 定量描述指标

规定时间→自然/运行/执行时间（占CPU）
可靠度R = 1 − 失效概率→初始为 0，随运行时间单调递增，趋向 1
指标英文全称含义
失效强度Failure Intensity单位时间内软件系统出现失效的概率
MTTFMean Time To Failure平均失效前时间（发生故障前正常运行的时间）
MTTRMean Time To Repair平均恢复前时间（故障后的修复时间）
MTBFMean Time Between Failures平均故障间隔时间 = MTTF + MTTR

记忆：MTTF 看"首次坏之前"，MTTR 看"坏了多久修好"，MTBF 看"两次故障之间"，MTBF = MTTF + MTTR。失效强度即失效率。

全系统可用性= MTTF / (MTTF + MTTR) × 100%
等价写法= MTBF / (MTBF + MTTR) = 1 − MTTR / (MTTF + MTTR)

▸ 这个公式是怎么来的？

  • 一个周期：正常运转 MTTF → 故障停机 MTTR → 再运转 MTTF → 再停机 MTTR… 一个"运转-修复"循环总时间 = MTTF + MTTR = MTBF。
  • 能用的占比：总时间里只有 MTTF 这段真正"能用"，其余 MTTR 在修。
  • 推出：可用性 = 能用的时间 ÷ 总时间 = MTTF / (MTTF + MTTR)。

为什么"可用 ≠ 可靠"：A 系统 MTTF=900、MTTR=100 → 可用 90%（少坏但修得慢）；B 系统 MTTF=99、MTTR=1 → 可用 99%（老坏但秒修）。只要 MTTR 足够短，可用性就能很高。

▸ 串并联系统可靠性（图中公式）

串联系统（一坏全坏）
R = R1 · R2 · … · Rn
并联系统（全坏才坏）
R = 1 − (1−R1)(1−R2)…(1−Rn)

图为串联「输入→R1→R2→…→Rn→输出」；并联「输入→(R1/R2/…/Rn 平行)→输出」。

▸ 为什么这样算（概率的"与"）

  • 串联 = 求"都对"：系统正常 ⇔ 所有部件都正常（独立事件同时发生，概率相乘）。例 R1=0.9、R2=0.8 → R=0.9×0.8=0.72（越串越不可靠）。
  • 并联 = 求"别全坏"：系统失效 ⇔ 所有部件都坏。先算全坏概率 F=(1−R1)(1−R2)…，再用 1 − F。例 F=0.1×0.2=0.02 → R=1−0.02=0.98（越并越可靠）。
  • 一句话：串联相乘（要全部好，变低）；并联"1 减全坏"（一个顶住，变高）。
02

可靠性建模

▸ 定义与影响因素

可靠性模型 = 为预计或估算软件可靠性所建立的可靠性框图和数学模型。

影响因素：运行环境、软件规模、软件内部结构、开发方法和环境、可靠性投入。

▸ 模型的组成

  • 模型假设：模型是对实际情况的简化/规范化（如测试代表实际运行剖面）。
  • 性能度量：模型输出量（失效强度、残留缺陷数）。
  • 参数估计方法：无法直接获取的度量（如残留缺陷数）通过参数估计间接确定。
  • 数据要求：模型要求一定的输入数据（可靠性数据）。

▸ 三大共同假设（考点）

代表性假设
  • 可用测试产生的可靠性数据预测运行阶段行为
独立性假设
  • 失效独立发生于不同时刻，互不影响
相同性假设
  • 所有失效后果（等级）相同，只考虑发生时刻

▸ 可靠性模型分类（了解概念）

种子法、失效率类、曲线拟合类、可靠性增长模型、程序结构分析、输入域分类、执行路径分析、非齐次泊松过程（NHPP）、马尔可夫过程、贝叶斯模型。

03

可靠性设计（重点 · 容错）

▸ 设计手段：避错 vs 容错

避错（排错）
  • 通过技术评审、系统测试、正确性证明，在系统正式运行前发现并改正错误
容错
  • 系统运行中发生一定硬件故障/软件错误时仍能正常工作的性能/措施，主要采用冗余消除故障影响

实践：设计阶段采取可靠性控制最有效、最经济、最重要。原则：在总体设计框架内、不与其他设计原则冲突；排在功能度、用户需求、开发费用之后考虑。

▸ 冗余技术（容错的基础）

在正常系统运行所需基础上增加一定数量资源（信息、时间、硬件、软件）。四种：

结构冗余
  • 静态、动态、混合
信息冗余
  • 如校验码、纠错码
时间冗余
  • 重试、重复执行
冗余附加
  • 用于冗余检测和维护

▸ 三大软件容错技术（高频考点）

技术思想
N 版本程序设计用 N 个功能相同程序同时执行，结果通过多数表决选出；N 个版本必须由不同人独立设计、用不同方法/语言/环境/工具，降低表决点相关错误概率
恢复块设计动态冗余（主动冗余）：故障检测→定位→恢复，用备用模块替换重跑；备用模块待机时并行工作=热备份，不工作=冷备份
防卫式程序设计不含传统容错，在程序中加错误检查代码 + 错误恢复代码，出错时撤销错误状态回到已知正确状态；策略=错误检测、破坏估计、错误恢复

▸ 双机容错

软硬结合方案（两台服务器 + 外接共享磁盘阵列 + 双机软件）。用心跳保持主备系统联系；心跳信号表明主系统故障或备机收不到主机心跳 → 高可用管理软件立即转移资源，备机替代工作。

工作模式：双机热备、双机互备、双机双工。

▸ 集群技术与负载均衡

集群：多台计算机协同工作，提高可用性与可靠性；特点=可伸缩、高可用、可管理、高性价比、高透明；分类=高性能计算集群、负载均衡集群、高可用性集群。

负载均衡常用技术：

  1. 基于特定软件（应用层，如 HTTP 重定向）
  2. 基于 DNS（传输层，主机名配多地址轮询）
  3. 基于 NAT（一个外网 IP 映射多个内网 IP）
  4. 反向代理（转发到内网多节点）
  5. 混合型
04

可靠性测试与评价

▸ 测试步骤

定义软件运行剖面→设计可靠性测试用例→实施可靠性测试

广义：为评价可靠性而运用建模、统计、试验、分析、评价等手段；狭义：为获取可靠性数据，按预先确定的测试用例在预期使用环境中测试（面向缺陷，以用户方式测试）。

▸ 可靠性评价三过程

选择可靠性模型→收集可靠性数据→可靠性评估与预测

选模型考虑：模型假设适用性、预测能力与质量、输出值能否满足评价需求、使用的简便性。数据是可靠性评价基础，主要在测试/实施阶段收集。辅助方法：失效数据图形分析、试探性数据分析技术。
