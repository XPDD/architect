01

演化的定义与重要性

▸ 定义

对架构进行修改和完善的过程，目的是使软件适应环境变化而进行的纠错性 + 完善性修改，不断迭代直至满足用户需求。本质是软件整体结构的演化，涵盖需求获取、建模、文档、实现、维护全生命周期。

通俗理解：不是"一个一个修 bug"，而是主动、结构化地调整系统骨架（改组件/连接件/约束），像重新装修而不是小修小补，且设计→演化→再设计→再演化循环进行。

▸ 为什么会有架构演化（核心：一切都在变）

① 业务 / 需求在变
  • 用户数暴涨（几千→几千万）→ 性能不够
  • 新功能、新业务不断进来 → 扩展困难
  • 商业模式变化 → 架构跟着调整
② 技术在变
  • 新技术（微服务/云原生/容器化），旧架构用不上
  • 换数据库、换框架、硬件升级
  • 旧风格有局限，须换成更能支撑业务的
③ 性能 / 可用性出问题
  • 访问量太大，单体顶不住 → 拆分、上缓存、做集群
  • 常宕机、响应慢 → 改造成高可用
④ 维护成本越来越高
  • 结构太耦合，改一处动全身，加功能很费力
  • 牵一发动全身 → 通过演化让结构更合理

例：大型网站架构演化 10 阶段（单体→垂直→缓存→集群→读写分离→反代+CDN→分布式→NOSQL→业务拆分→分布式服务），就是业务与用户量持续增长、不断推动架构演化的结果。

▸ 架构三大要素与降低演化成本原因

架构定义包含组件、连接件、约束三要素；演化就是对三者的添加、修改、删除。

  • 形式化/可视化表示提高可构造性，便于演化。
  • 结构/配置/约束信息帮助开发人员充分考虑未来演化。
  • 组件间耦合描述有助于系统动态调整。

▸ 三大要素详解：是什么 · 为什么 · 怎么办

组件 Component —— "系统的零件"
  • 是什么：承担具体功能的计算单元/数据单元（模块、服务、进程、数据库表），是架构里"被调度的东西"。
  • 为什么：组件是功能与独立性的载体，它的内聚与耦直接决定系统好不好改、好不好重。
  • 怎么办：拆出高内聚、低耦合的组件；演化 = 增删组件（AO/DO）、拆分/聚合组件。
连接件 Connector —— "零件之间的接口/通道"
  • 是什么：组件之间交换数据/传递控制/调用服务的机制（方法调用、消息、事件、RPC、管道）。
  • 为什么：它界定了组件如何协作；连接件的类型与协议决定了系统能否动态调整、能否松耦合。
  • 怎么办：用清晰、标准、可替换的连接件；演化 = 增删/改消息（AM/DM/SMO）、改收发对象（OM/CMM）、改复合片段（AF/DF/FTC）。
约束 Constraint —— "必须遵守的规则"
  • 是什么：对组件、连接件的限制与配置规则（性能指标、安全策略、接口契约、部署要求）。
  • 为什么：约束把"模糊的设计"变成可验证的边界，保证设计满足质量属性（性能/安全/兼容）。
  • 怎么办：显式记录约束；演化 = 添加/删除约束（AC/DC），改动后须验证是否仍满足约束。
三者关系 & 演化操作
  • 关系：组件用什么；连接件怎么连；约束能不能这么连。
  • 演化：对三者做增、删、改——组件（增删/拆分聚合）、连接件（消息/片段改动）、约束（增删条款）。
  • 一句话：改"零件"（组件）、改"接口"（连接件）、改"规矩"（约束），三者共同支撑架构的动态调整与平滑演进。

▸ 四类演化（基于顺序图）

演化类英文（全称 / 缩写）含义典型操作与场景
对象演化 Object Evolution
AO=Add Object / DO=Delete Object		 顺序图中对象的增删（对象=组件实体） 新增功能、提升灵活性 / 移除功能、合并降低复杂度
消息演化 Message Evolution
AM=Add Message 增 / DM=Delete Message 删 / SMO=Swap Message Order 换序 / OM=Overturn Message 反转收发 / CMM=Change Message Module 改收发对象		 对象之间交互行为的增删改 增删交互行为、改变交互关系、修改交互本身
复合片段演化 Interactive Fragment Evolution（复合片段=控制流)
AF=Add Fragment 新增 / DF=Delete Fragment 删除 / FTC=Fragment Type Change 改类型 / FCC=Fragment Condition Change 改执行条件		 对象交互"控制流"（交互片段）的增删改 DF 与 AF 互逆；FTC≈删+添组合；FCC 改条件
约束演化 Constraint Evolution
AC=Add Constraint 添加 / DC=Delete Constraint 删除		 直接增删约束信息（文字描述） 需判断设计是否满足新约束 / 去除不必要约束

记忆：对象管"零件"、消息管"交互"、复合片段管"控制流"、约束管"规则"。所有缩写首字母都来自英文动词（Add/Delete/Swap/Overturn/Change…）。

03

演化方式分类

▸ 三种分类维度

  • 按实现方式/粒度：基于过程和函数、面向对象、基于组件、基于架构。
  • 按研究方法：支持演化的（代码模块化、内聚耦合、重构）、版本/工程管理工具、架构变换形式方法、演化成本收益分析。
  • 按是否运行期：静态演化 vs 动态演化。

▸ 静态演化（设计时 · 运行前）

软件理解→需求变更分析→演化计划→系统重构→系统测试

对应维护：更正性、适应性、完善性维护。原子演化操作 = 基于 UML 的最小粒度修改，每步形成演化中间版本；可维护性度量（基于组件图）、可靠性评估（基于用例图/部署图/顺序图）。

▸ 动态演化（运行期，不需停机）

两大来源：①软件内部执行导致的体系结构改变（如在线游戏动态创建房间）；②外部请求对软件的重配置（如内核运行时加载不重启）。

动态性三级：交互动态性、结构动态性（主流）、架构动态性。

内容四方面：属性改名、行为变化、拓扑结构改变、风格变化（风格变化只能变为衍生风格）。

实现技术：DSA（动态软件架构）、DR（动态重配置）。DSA 实施四步：捕捉分析需求 → 生成演化策略 → 实施演化 → 演化后评估。DR 模式：主从、中央控制、客户端/服务器、分布式控制。

04

演化原则（18 条）与评估

▸ 18 条原则（关键词）

成本可控、进度可控、风险可控、主体维持、总体结构优化、平滑演化、目标一致、模块独立演化、影响可控、复杂性可控、有利于重构、有利于重用、设计原则遵从、适应新技术、环境适应、标准依从、质量向好、适应新需求。

▸ 演化评估方法

  • 演化过程已知（正向）：对演化过程度量，比较结构差异及外部质量属性变化（度量、监控、分析关键演化过程）。
  • 演化过程未知（逆向）：根据演化前后度量结果逆向推测架构变化及与质量属性关联。
05

大型网站架构演化（10 阶段）

①单体→②垂直→③缓存→④服务集群→⑤库读写分离
⑥反代+CDN→⑦分布式文件/库→⑧NOSQL+搜索引擎→⑨业务拆分→⑩分布式服务

各阶段组件（图中细节）：CDN 服务器、反向代理、负载均衡调度服务器、应用服务器 n/2/1（应用程序/统一数据访问模块/本地缓存）、分布式缓存/文件/数据库、搜索引擎、NoSQL。

06

软件架构维护

▸ 三个方面

架构知识管理

对设计决策来源做文档化；架构知识 = 架构设计 + 架构设计决策（说明为何这样设计）；侧重于静态演化

架构修改管理

建立隔离区域降低修改对其他部分影响；明确修改规则、类型、影响范围与副作用

架构版本管理

为演化版本控制、使用、评价提供依据，为演化量化度量奠定基础
