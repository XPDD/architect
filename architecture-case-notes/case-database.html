阅读以下关于缓存与数据库一致性的叙述，回答问题 1 至问题 3。
P3 · 数据库设计
【说明】

某大型电商平台为缓解订单详情页的高并发读压力，采用 Redis 缓存 + MySQL 的 cache-aside（旁路缓存）架构：应用先读缓存，未命中再读数据库并回填缓存；写操作先更新数据库，再更新/失效缓存。为应对高并发下的缓存异常，团队引入布隆过滤器（用于解决缓存穿透——大量非法/不存在数据的请求绕过缓存直达数据库）；对热点 key 失效则采用互斥锁 / 逻辑过期（解决缓存击穿）；同时为支撑秒杀抢购，使用 Redis 分布式锁保护关键资源。

  • 李工提出缓存与数据库的一致性方案：实时同步更新。
    张工提出异步准实时更新。
  • 王工使用多线程处理：线程 1 负责写入缓存，线程 2 负责读取缓存。
问题 1请写出 cache-aside 架构中「读取数据」「写入数据」的完整流程，并分析多线程下可能产生的一致性风险。9 分

请写出旁路缓存（cache-aside）架构读取数据与写入数据的过程；并说明王工的多线程读写（写线程未更新完缓存时读线程可能读到旧数据）造成的不一致问题成因，至少给出 3 种解决办法。

参考答案
  • 读流程：①查询缓存是否有目标数据 →②命中则返回目标数据 →③未命中则访问数据库查询 →④将查询到的数据更新到缓存 →⑤返回目标数据。
  • 写流程：①更新数据库中的目标信息 →②将更新后的数据写入缓存（确保一致性）。
  • 一致性风险成因：读写线程并发导致缓存与数据库不一致——如写线程尚未更新完缓存时，读线程读到了旧数据。
  • 解决办法：①加锁同步——对缓存操作加互斥锁，确保读写互斥；②设置缓存过期时间——强制定期刷新缓存，缩小不一致时间窗口；③延迟双删——写数据库后延迟再次删除缓存，防止旧数据残留；④异步队列——将缓存更新操作串行化到队列处理，避免并发冲突。
问题 2缓存与数据库一致性：实时同步更新 vs 异步准实时更新，应如何选择？请说明选择依据。8 分

李工建议实时同步更新，张工建议异步准实时更新。请分别简述两种方案的基本思路，并说明本场景（读多写少、对响应速度要求极高）应选哪种方案及原因。

参考答案
  • 实时同步更新：每次数据更新立即同步更新缓存与数据库，确保两者一致，适合一致性要求高的场景，但性能开销大。
  • 异步准实时更新：数据库更新后，稍后通过异步机制更新缓存（批量/定时同步），数据在一定时间内趋于一致，适合对实时性要求不高的场景。
  • 选择：本场景应选异步准实时更新。原因是订单详情类功能读操作远多于写操作、对系统响应速度要求极高，异步更新能减少实时同步的性能开销，保证系统高效与用户体验。
问题 3请区分缓存穿透与缓存击穿，并说明布隆过滤器如何解决缓存穿透，及 Redis 分布式锁。8 分

请先指出缓存穿透与缓存击穿的区别；再解释布隆过滤器的工作原理与优缺点，并说明它如何解决缓存穿透（而非缓存击穿）；最后说明基于 MySQL 与基于 Redis 的分布式锁各自的适用性，以及 Redis 分布式锁的一种死锁场景。

参考答案
  • 缓存穿透 vs 击穿：穿透＝查询根本不存在的数据（如恶意请求不存在 ID），缓存永远不命中，每次都打数据库；击穿＝某个热点 key 过期的瞬间，大量并发请求同时打到数据库。穿透用布隆过滤器/缓存空值解决；击穿用互斥锁/逻辑过期解决。
  • 布隆过滤器：空间效率高的概率型数据结构，用多个哈希函数把数据映射到位数组。判断存在时检查多个哈希值对应位是否全为 1：有任一为 0 → 一定不存在；全为 1 → 可能存在（有假阳性）。优点：内存小、查询快、适合大规模；缺点：有假阳性、无法删除已添加数据。
  • 解决缓存穿透：把可能存在的数据 key 预先放入布隆过滤器；请求到来先查布隆过滤器，若判断「一定不存在」直接返回，避免无效/非法请求反复打数据库，从而缓解缓存穿透。
  • MySQL 锁缺点：性能瓶颈、单点故障、锁粒度问题、数据一致性、扩展性差、容错性差；Redis 锁更适合高并发分布式场景，配合过期时间与续期使用。
  • 死锁场景：客户端 A 获锁后执行任务，执行时间超过锁有效期，锁自动过期释放，客户端 B 获得锁；A 尚未完成任务仍以为自己持锁继续执行，导致多个客户端对资源并发操作混乱。
