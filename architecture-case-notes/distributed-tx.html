▸ 核心要点
1先把题目翻译成大白话

银行把系统拆成了 7 个微服务，各自有自己的数据库。一次"放款"要同时做三件事：账户服务扣钱、放款服务开借据、风控服务记快照——分属三个服务、三个库。问题来了：数据库自带的事务（ACID）只能管同一个库，跨服务管不了。

如果第二、三步失败了，第一步的钱却扣了 → 就"错账"了（钱少了/多了）。所以要一个能在多个服务之间保证一致的机制，这就是"分布式事务"。

一句话：单库事务管一个库；分布式事务管多个服务/库。主线：先看要不要强一致 → 强一致选 XA 或 TCC → 允许异步最终一致就用本地消息表+MQ → 长流程可补偿用 Saga。

2名词速查（不懂的词看这里）
事务 / ACID一组操作"要么全成功、要么全失败"，中途失败会回滚
分布式事务一次操作跨多个服务/多个数据库，也要保证一致
2PC（两阶段提交）先"准备"、再"提交"两个阶段——大家都准备好，我才说提交
XAX/Open 定义的 2PC 标准接口，由数据库层面支持、事务管理器统一协调
TM / RMTM＝事务管理器（协调者）；RM＝资源管理器（各数据库）
TCCTry-Confirm-Cancel：在业务层面把操作拆成"预留 / 确认 / 取消"三步
补偿撤销已经做过的操作（做一个"反向"操作把钱/库存退回来）
幂等同一操作执行一次或多次，结果都一样（防止重复扣款/重复发送）
空回滚Try 还没执行，却先收到了 Cancel（要能安全忽略）
悬挂Cancel 比 Try 先到，之后 Try 又来了（要防止"回滚后又被执行"）
强一致 / 最终一致强一致＝任何时候都一致；最终一致＝允许暂时不一致，过一会儿会自动对齐
Saga把长事务拆成一串本地小事务，失败就按相反顺序补偿
编排 / 协同编排＝有"总指挥"按顺序调度；协同＝各服务靠事件自己接力
本地消息表 + MQ业务和"待发消息"写进同一个库同一个事务，再异步可靠地发到消息队列
3XA（两阶段提交 2PC）——数据库层面

原理：一个"总协调者"（TM）管着几个数据库（RM），分两步走：

  • 阶段一 prepare（准备）：协调者让每个数据库都"把事务做完但先别提交"，并锁住相关资源，等大家报告"我准备好了"。
  • 阶段二 commit / rollback：所有人都 OK → 全部提交；只要有一个失败 → 全部回滚。

生活类比：几个人吃饭 AA 付钱，收银员说"大家先把钱备好举手（prepare）"，都举手了才"一起付（commit）"；有人没备好就都别付。备好到付款期间，这笔钱是被冻住的（资源被锁）。

◆ XA 两阶段提交流程
事务管理器 TM（协调者）
↓ 阶段一：PREPARE
账户库 RM
做完但未提交·锁资源
放款库 RM
做完但未提交·锁资源
风控库 RM
做完但未提交·锁资源
↓ 都返回"就绪" → 阶段二：COMMIT（有失败则全部 ROLLBACK）
全部提交 → 全局一致
任一失败 → 全部回滚
XA 的特点说明
一致性强隔离、强一致（全局事务）
性能资源锁定时间长、性能差；协调者是单点
侵入性低，靠数据库支持，对业务代码基本无侵入
适用低频、强一致的场景：对账、批量处理
4TCC（Try-Confirm-Cancel）——业务层面

原理：不依赖数据库的锁，而是在每个服务的业务代码里把一个操作拆成三个方法：

  • Try（预留）：先"占住"资源，但不真正完成。如：冻结额度、锁定库存。
  • Confirm（确认）：所有服务的 Try 都成功后，真正执行。如：真正扣款、正式开借据。
  • Cancel（取消）：只要有一步 Try 失败，就调用所有已 Try 成功服务的 Cancel，把预留释放掉。

生活类比：订酒店"先锁房（Try）"，到店入住才算"确认（Confirm）"；不去了就"取消（Cancel）"退掉。房间只要被锁住，就不怕被别人抢——这就是 TCC 用"预留"替代"数据库锁"的思路。

注意：TCC 的三个操作都必须是幂等的，还要处理空回滚和悬挂两个坑。

◆ TCC 三阶段
① Try 预留
冻结额度 / 锁库存 / 预生成借据
↓ 全部 Try 成功
② Confirm 确认
真正扣减 / 正式入账（幂等）
↓ 任一步 Try 失败
③ Cancel 取消
释放预留（幂等）
5XA vs TCC（题目问题 1 的核心对比）
XA 两阶段提交
  • 一致性：强隔离、强一致
  • 性能：锁资源重、性能差、协调者单点
  • 侵入性：低（靠数据库）
  • 适用：低频、强一致（对账、批量）
VS
TCC 补偿事务
  • 一致性：最终一致，靠业务保证
  • 性能：无长事务锁、性能较好
  • 侵入性：高（要实现 Try/Confirm/Cancel）
  • 适用：资金类核心链路、可自定义补偿
维度XA 两阶段提交TCC 补偿事务
一致性强度强隔离、强一致（全局事务）最终一致，靠业务层面保证
性能资源锁定重、性能差；协调者单点无长事务锁、性能较好
侵入性低，对业务基本无侵入高，需实现 Try / Confirm / Cancel 三个方法
适用场景低频、强一致的场景（对账、批量）资金类核心链路，可自定义补偿

本题选型："放款"是资金核心、频率中等，优先用 TCC 保证资金强一致，再辅以对账兜底。（低频、对账类才考虑 XA。）

6Saga：长流程的补偿式事务（是什么 + 为什么 + 流程）

是什么：Saga 把一个"跨多个服务、步骤多、耗时长"的大事务，拆成一串本地小事务 T1→T2→…→Tn；每个 Ti 都是单个服务里又快又短的事务，做完立刻提交。只要某一步失败，就反向执行"补偿操作" C（撤回已完成的步骤），把整体效果抵消掉。

为什么要用：XA 要锁资源、慢；而长流程又不能一直锁着不放。于是换个思路——不锁、先做、错了再补。注意它是"补偿"而不是数据库的"回滚"：扣款错了不是 rollback，而是业务上再转一笔钱回来，所以补偿必须"业务上可定义、且可重复执行（幂等）"。

生活类比：出门旅行依次订"机票 → 酒店 → 租车"；若租车失败，就依次退酒店、退机票——每一步都有对应的"退"。

6.1 编排模式（Orchestration）—— 有"总指挥"

由一个编排服务当总指挥，按顺序调用各服务、记录每步状态；失败就按相反顺序调用补偿。集中可控、状态清晰、便于审计，银行资金场景常用。

编排服务 Orchestrator
总指挥 · 记录每步状态
↓ 依次调用（成功就继续）
T1 账户扣款 ✓
→
T2 生成借据 ✓
→
T3 记录风控 ✗ 失败
↓ 某步失败 → 按相反顺序执行补偿
C2 作废借据
→
C1 退回扣款

6.2 协同模式（Choreography）—— 靠"事件接力"

没有总指挥，各服务做完自己那步就发一个事件，别的服务订阅事件、自己决定下一步；失败则发失败事件，相关服务各自执行补偿。去中心化、松耦合，但链路长、整体状态难追踪。

◆ 协同模式流程（事件驱动）

T1 扣款完成
↓ 发布事件「贷款专户已扣款」
放款服务（订阅到该事件）
T2 生成借据
↓ 发布事件「借据已生成」
风控服务（订阅到该事件）
T3 记录快照 ✗ 失败
↓ 发布失败事件「快照记录失败」
放款 / 账户 各自订阅 → 分别执行补偿

6.3 两种模式对比

维度编排模式（Orchestration）协同模式（Choreography）
控制方式中心编排器统一调度各服务靠事件自发驱动下一步
耦合度服务只与编排器交互，较低服务彼此订阅事件，事件耦合
状态可追踪编排器集中记录，清晰、利于审计分散在各服务，难追踪
主要风险编排器逻辑集中、可能成单点链路长、易"事件风暴"
适用流程复杂、需审计（银行资金）步骤少、简单、追求松耦合

6.4 银行资金场景必须注意的两个约束（含为什么）

  • ① Saga 没有隔离性：各步提交后立刻对别人可见，会暴露"中间状态"（如"已扣款、借据未生成"），资金场景若被读到，可能误判或重复操作。
    为什么：Saga 是"先提交、失败再补"，不像数据库事务能锁住中间态。
    应对：语义锁 / 资源预留（先冻结、确认后再扣）、用状态标记（"处理中"不对外可操作）、避免读中间态。
  • ② 补偿必须完备且可幂等重试：每个正向操作都要有能抵消它的补偿，且补偿本身可能失败、需要重试，否则会资金不一致。
    为什么：补偿也是网络调用，会失败；重试又可能重复执行。
    应对：正/逆向操作成对设计、补偿表登记状态、幂等键去重、失败重试 + 死信 + 人工兜底，并防"空补偿 / 悬挂"。

6.5 补偿怎么设计（落地要点）

  • 成对设计：正向 Ti 与逆向 Ci 一一对应（扣款↔退款、生成借据↔作废借据）。
  • 补偿幂等：同一补偿执行多次只生效一次（用幂等键 / 唯一索引 / 状态判断）。
  • 补偿可重试：补偿失败要能重试，超限进死信并转人工处理。
  • 记录状态：用状态机 / 补偿表记录每步是否完成、是否已补偿，防止漏补或重复补。
  • 防悬挂：避免"补偿先于正向执行"（如超时重试导致正向操作迟到），用状态校验拦住。

Saga vs TCC：两者都是"预留/补偿"思路，但 TCC 有 Try 预留资源（准隔离）、要写三个方法、侵入大；Saga 无隔离、只需"正向 + 补偿"，更适合长流程。资金核心要强一致 → 优先 TCC；长流程能容忍中间态 → 用 Saga。

7本地消息表 + MQ：允许异步时用（还款→征信报送）

征信报送"允许异步、最终一致、不可漏报"，就没必要用重量级的强一致方案，用可靠消息即可：

  • ① 业务表与"待发消息表"同一个库、同一个事务写入 → 保证"业务 + 消息"原子性。
  • ② 独立任务扫描消息表，把待发消息投递到 MQ。
  • ③ 消费端处理成功后，回改消息状态。
  • ④ MQ "至少一次"投递，消费端按业务唯一键（还款流水号）做幂等。
◆ 可靠消息最终一致
还款业务 + 消息表
同库同事务写入
↓ 扫描消息表
投递到 MQ
失败重试·超时进死信队列
↓ 至少一次投递
征信报送服务消费
按唯一键幂等落库 → 回改消息状态
要解决的办法
消息不丢投递失败重试 + 消息表状态机推进；长时间未送达进死信队列
不重复消费消费端以业务唯一键（还款流水号）做幂等（唯一索引 / 去重表）

◆ 费曼

分布式事务说人话：一群人要一起办成一件事，怕有人办一半，就得有"约定"。XA 是最"死板"的约定：所有人都先把事做好但先别交（prepare），我说交才一起交（commit）——期间占着资源，慢但绝对不会错，靠数据库实现。TCC 更"灵活"：先占坑（Try）、再拍板（Confirm）、出事就撤（Cancel）——快、适合钱多的核心链路，但每个服务都得自己写好"占坑/拍板/撤坑"三件事。Saga 是"走一步看一步，错了就按原路退回去"。如果只是"允许晚点同步、但不能漏"，那就用最省事的 本地消息表 + MQ：把"要发的消息"和业务记在同一个账本里，保证消息一定发得出去，收的人自己去重就行。

▸ 总结

跨服务没法用单库事务，才需要分布式事务。XA＝数据库层两阶段提交（prepare→commit，强一致、慢、无侵入、适低频）；TCC＝业务层 Try/Confirm/Cancel（预留→确认→取消，最终一致、快、侵入大、适资金核心，需幂等/防空回滚与悬挂）；长流程用 Saga（编排 vs 协同，注意无隔离+补偿完备）；允许异步用本地消息表 + MQ（同库同事务写入，不丢靠重试+死信，不重靠唯一键幂等）。放款选 TCC，征信报送选本地消息表+MQ。
