▸ 核心要点
1先把题目翻译成大白话

某市政务平台日均 800 万请求，已经出过三次事故：核心数据库挂了 3 小时、某接口被高并发压垮、缓存单点故障引发雪崩。政府要求：年度可用性 ≥ 99.95%、RTO ≤ 30 分钟、RPO ≤ 5 分钟。

翻译一下就是：尽量别挂（冗余/心跳/隔离）、被压也不崩（限流/熔断/降级）、挂了要能快速恢复且少丢数据（容灾/备份）、出问题能看得见（监控）。主线：不挂 → 抗压 → 快恢复 → 可观测。

2名词速查（不懂的词看这里）
可用性系统在需要时能正常服务的时间比例（如 99.95%）。"病了多久能好"
可靠性系统一段时间内不出故障的能力。"从不生病"
单点故障 SPOF某个组件一挂、整个系统就挂
冗余多准备几份/几个，坏一个还有备份顶上，消除单点
故障转移 failover主挂了，自动切到备
心跳检测节点之间定期"报平安"，超时没报就认为它挂了
隔离把故障关在局部，不让它扩散（舱壁思想）
雪崩一个地方出问题，导致整个系统连锁崩盘
限流限制进入的流量，保护自己不被冲垮
熔断下游坏了先"跳闸"，不再请求它，给它恢复时间
降级压力大/故障时，主动关掉非核心功能，保核心
RTO故障后多久能恢复（恢复时间目标）
RPO能容忍丢多少数据（数据丢失目标）
容灾同城双活 / 异地灾备等"备用场地"方案
黄金信号延迟、流量、错误、饱和度（监控四项核心指标）
3作用一：冗余（消除单点）

作用：通过多副本 / 多节点消除单点故障，某个节点坏了还有别的顶上，做到故障时自动切换、服务不中断。

生活类比：家里备一把备用钥匙；一盏灯坏了，另一盏还亮着。

◆ 单点故障 vs 冗余
一个实例（单点）→ 挂了就全挂
↓ 加冗余
实例A ✓
实例B ✓（备份）
实例C ✓（备份）
前面的"负载均衡"自动把流量分给还活着的实例

本平台至少三种冗余部署方式（记住这 6 种）：

1
应用多实例 + 负载均衡
  • Web/服务多开几个，前面挂 LB 分流
    • 2
    数据库主从 / 多副本
  • 一主多从，主挂了从顶上
    • 3
    Redis 哨兵 / 集群
  • 缓存多节点，避免缓存单点
    • 4
    消息队列集群
  • MQ 多副本，防止消息服务单点
    • 5
    存储多副本
  • 文件/对象存储多副本保存
    • 6
    跨机房 / 跨可用区部署
  • 机房级容灾，一个机房挂了还有别的
    • 4作用二：心跳检测（发现故障、驱动切换）

    作用：节点之间周期性发送心跳判断对方是否存活；一旦超时没心跳，就判定它故障，驱动故障转移并剔除坏节点。它是"冗余"能自动生效的眼睛——没有心跳，冗余只是摆设，不知道谁挂了。

    ◆ 心跳驱动的故障转移流程
    主节点每隔几秒发一次"心跳"（我还活着）
    ↓ 备节点 / 监控持续监听
    连续超时未收到心跳 → 判定主节点故障
    ↓
    触发故障转移：从备节点选出新主
    →
    摘除故障节点 + 告警
    5作用三：隔离（把故障关起来，防雪崩）

    作用：把故障限定在局部，防止"单点故障 → 连锁反应 → 整个系统雪崩"。核心思想是"舱壁"：船底破一个舱，水进不到别的舱，船就不沉。

    三种常见隔离：

    • 舱壁 / 线程池隔离：给每个下游服务分配独立线程池；某个下游变慢，只占满它自己的池，不会拖垮所有请求。
    • 服务隔离：核心服务与非核心服务分开部署/分资源，非核心出事不影响核心。
    • 超时隔离：给每个调用设超时，慢就快速失败，不无限等待把资源耗光。
    ◆ 没有隔离 vs 有隔离
    没有隔离：下游C变慢 → 线程全被占满 → 整个服务卡死（雪崩）
    ↓ 加隔离
    下游A 独立池
    下游B 独立池
    下游C 慢（只占自己的池）
    C 慢也只影响 C，A/B 正常，系统整体不崩
    6被压也不崩：限流 / 熔断 / 降级
    机制白话适用 / 实现要点
    限流限制进入的流量，保护自己不被冲垮有明确容量上限时；令牌桶 / 滑动窗口；建议网关 + 接口两级限流
    熔断下游坏了就"跳闸"，先别再请求它错误率超阈值打开断路器，快速失败，给下游恢复时间，防故障扩散
    降级压力大时主动关非核心功能，保核心返回兜底数据/降级文案，保证核心链路可用

    三者关系：入口限流 → 中间熔断 → 末端降级——分层保护，从外到内逐级兜底。

    ◆ 分层保护
    ① 限流：挡住超额流量（入口）
    ↓
    ② 熔断：保护下游健康（中间）
    ↓
    ③ 降级：保核心体验（末端）
    7快恢复 + 少丢数据：RTO / RPO 与数据库容灾

    RTO（恢复时间目标）＝"多久能恢复"；RPO（恢复点目标）＝"最多丢多少数据"。目标越小，要求的方案越强。

    ◆ RTO / RPO 含义
    故障发生
    —— RPO（可丢的数据时段）——▶
    恢复完成
    ◀————— RTO（停机时长，≤30min）—————▶
    层做法对应目标
    高可用数据库一主多从 / 高可用集群，主库故障自动切换（MHA / Orchestrator），读写分离分摊压力保证 RTO（自动切换 ≤30min）
    容灾同城双活 / 异地灾备，用 WAL 日志或同步复制保证数据不丢满足 RPO（≤5min）
    备份全量备份（每日）+ 增量 / 归档日志（实时），并定期异机备份兜底恢复能力
    演练季度/半年做一次 RTO / RPO 演练，验证主备切换时长与数据完整性，形成恢复手册并定责到人验证目标真的能达成
    8看得见故障：可观测监控体系
    • 指标：采用 Google SRE 的四个黄金信号——延迟、流量、错误、饱和度；再补充核心业务链路的可用性指标。RED / USE 方法可作细分参考。
    • 告警：分级告警（P1～P4）+ 值班轮值 + 超时升级；配合可视化看板与链路追踪辅助定位。
    • 职责：明确 SRE / 运维 / 开发的责任矩阵，重大故障复盘闭环。
    • 演练：定期做混沌工程 / 故障演练（注入主机宕机、依赖故障），检验架构韧性，把可用性纳入 OKR 持续改进。

    → 本话题有独立专篇：可观测性 · 监控告警与持续提升可用性（三支柱 / 四黄金信号 / SLI·SLO·错误预算 / 完整闭环）

    9回到题目四小问（要点速记）
    问题要点
    问题1冗余＝多副本消除单点、自动切换；心跳＝判断存活、驱动故障转移；隔离＝把故障限局部、防雪崩。冗余方式至少三种：应用多实例+LB / 数据库主从 / Redis 哨兵集群 / 消息集群 / 存储多副本 / 跨机房
    问题2限流保护自身、熔断保护下游、降级保核心；关系"入口限流→中间熔断→末端降级"
    问题3一主多从/集群自动切换 + 同城双活/异地灾备 + 全量&增量备份 + RTO/RPO 演练（对应 ≤30min / ≤5min）
    问题4四黄金信号 + 分级告警 + 责任矩阵 + 混沌演练，纳入 OKR 持续提升
    ◆ 费曼

    可用性保障说人话：想让系统"打不死"，就四招。冗余＝多请几个替补，主力倒了替补上（应用多开、数据库主备、Redis 集群、跨机房）；心跳＝队友定期喊一声"我还在"，谁不吭声就当它倒了，赶紧换人；隔离＝把每个下游关进单独的小房间（线程池/超时），一个房间失火不会烧到全船；限流熔断降级＝门口限人数、下游坏了先别打电话、忙不过来先丢掉不重要的功能。真挂了怎么办？靠容灾备份，并且用 RTO（多久恢复）和 RPO（最多丢多少）来定标准；最后用监控四黄金信号把问题"看得见"，再靠演练不断变强。

    ▸ 总结

    冗余＝多副本消除单点、自动切换（至少记：应用多实例+LB、数据库主从、Redis 哨兵/集群、消息集群、存储多副本、跨机房）；心跳＝周期探测存活、驱动故障转移与剔除；隔离＝线程池/服务/超时隔离，把故障关在局部防雪崩；限流→熔断→降级＝入口/中间/末端分层保护；恢复靠容灾（同城双活/异地灾备）+ 备份 + 演练，用 RTO/RPO 定标准；监控用四黄金信号（延迟/流量/错误/饱和度）+ 分级告警 + 责任矩阵 + 混沌演练。
