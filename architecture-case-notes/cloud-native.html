▸ 核心要点
1云原生架构内涵

云原生架构是基于云原生技术的一组架构原则和设计模式的集合，旨在把云应用中的非业务代码部分最大化剥离，让云设施接管大量非功能特性（弹性、韧性、安全、可观测性、灰度等）。

  • 云原生代码三部分：业务代码、三方软件、处理非功能特性的代码（剥离到 IaaS / PaaS）。
  • 注意：不是所有非功能都能剥离，如「易用性」还不能剥离。
  • 三大特点：代码结构发生巨大变化、非功能性特性大量委托、高度自动化的软件交付。
2云原生架构原则（7 条）
  • 服务化：拆分为微服务/小服务，分别迭代。
  • 弹性：部署规模随业务量变化自动伸缩。
  • 可观测：通过日志、链路跟踪、度量等手段。
  • 韧性：软硬件组件异常时软件的抵御能力。
  • 所有过程自动化：标准化+自动化，配置数据自描述、面向终态交付。
  • 零信任：默认不信任网络内外任何人/设备/系统，以身份为中心，基于认证授权重构信任。
  • 架构持续演进：架构本身要具备持续演进能力。
3主要架构模式（7 种）
模式要点
服务化微服务/小服务；代码模块关系与部署关系分离，每接口可单独扩缩容
Mesh 化把中间件框架（RPC/缓存/异步消息）从业务进程分离，业务只留很「薄」的 Client
Serverless把「部署」动作收走，应用整个运行委托给云
存储计算分离暂态数据(session)、结构化/非结构化持久数据都用云服务保存
分布式事务大粒度业务访问多微服务带来的数据一致性，需按场景选合适模式
可观测Logging + Tracing + Metrics 三方面
事件驱动应用/组件间集成架构，用于服务解耦、增强韧性、数据变化通知

可观测架构三支柱：Logging（多级别详细信息跟踪，开发者主动提供）、Tracing（请求从前端到后端的完整调用链路，分布式场景尤其有用）、Metrics（对系统量化的多维度度量）。

4微服务设计约束（4 类）
  • 个体约束：功能在业务域上相互独立，低耦合、单一职责。
  • 横向关系（服务间）：可发现性、可交互性，一般需要服务注册中心。
  • 纵向约束（服务与数据层）：数据存储隔离——数据是微服务私有资产，访问必须通过其 API。
  • 全局分布式约束：故障发现时效性和根因精确性是核心诉求。
5云原生相关技术
1
容器技术
  • 标准化软件单元，应用+依赖打包，不受环境限制
  • Kubernetes＝容器编排事实标准：资源调度、自动修复、服务发现、弹性伸缩、声明式 API 等
2
Serverless
  • 特征：全托管、通用性、自动弹性伸缩、按量计费
  • FaaS（函数计算）最具代表性，函数事件驱动触发
  • 关注点：计算资源弹性调度、负载均衡和流控、安全性
3
Service Mesh
  • 把连接/安全/流量控制/可观测下沉为平台基础设施
  • 应用与平台基础设施解耦；服务代理截获请求，策略在控制平面(Control Plane)配置
4
主要微服务技术
  • Dubbo(阿里 RPC) / Spring Cloud / Eclipse MicroProfile
  • Tars(腾讯) / SOFAStack(蚂蚁金融级) / DAPR(微软可移植运行时)
6案例分析 — 旅行公司云原生改造

两个问题：技术体系不同需整合、节假日高并发流量。分三个阶段：

  • 第一阶段：提升集群资源利用率、降成本；多套旧系统合并到私有云平台，IaaS/PaaS 虚拟化封装自动化。
  • 第二阶段：保障服务稳定性；基于公有云+私有云+离线专属云，用声明式 API、不可变基础设施、服务网格、容器服务构建弹性应用。
  • 第三阶段：基础组件/服务云原生改造，实现跨地域跨云自动化灾备、自动部署，向 DevOps 演进。

◆ 费曼

云原生说人话：把应用里「跟业务无关的杂活」——弹性、安全、监控、灰度这些——尽量外包给云平台，自己只写业务代码。7 原则记要点：服务化、弹性、可观测、韧性、自动化、零信任、持续演进。7 模式里最容易混的是 Mesh 化（把中间件剥离出业务进程） vs Serverless（把整个部署都交给云）。可观测三兄弟：日志(Logging)看细节、链路(Tracing)看全程、指标(Metrics)看度量。

▸ 总结

云原生＝最大化剥离非业务代码，让云接管非功能特性；代码三部分业务/三方软件/非功能处理；7 原则（服务化/弹性/可观测/韧性/自动化/零信任/持续演进）；7 模式（服务化/Mesh/Serverless/存储计算分离/分布式事务/可观测/事件驱动）；微服务 4 约束（个体/横向/纵向/全局）。重点掌握内涵+原则+模式，服务于论文写作。
