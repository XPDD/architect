▸ 核心要点
1SOA 与微服务的区别
维度SOA微服务
粒度服务粒度粗（如「员工管理系统」）服务粒度细（拆为员工信息/考勤/假期/福利等）
通信模式用 ESB 做服务路由/消息转换，重量级统一 RESTful / RPC 协议，无需 ESB
服务交付无特殊要求，考虑兼容已有系统要求快速交付：自动化测试、持续集成、自动化部署
应用场景庞大、复杂、异构的企业级系统（靠 ESB 兼容）快速、轻量、基于 Web 的互联网系统

结论：SOA 与微服务本质是两种不同的架构设计理念，只在「服务」点上有交集，无孰优孰劣，只是场景不同。把微服务生搬硬套到企业级系统，改造成本可能远超 SOA。

2SOA 参考架构 — 六大类服务
类别职责 / 细分
业务逻辑服务实现业务逻辑：业务应用服务、业务伙伴服务、应用和信息资产
控制服务实现人、流程、信息集成及集成逻辑
连接服务通过 ESB 提供各架构元素服务间的连接性
业务创新和优化服务监控业务性能，应对市场变化（以 BPM 为核心）
开发服务贯穿软件开发生命周期的开发平台（建模/设计/实现/测试）
IT 服务管理基础设施管理能力：安全/目录服务、系统管理、资源虚拟化
3协议与规范 — UDDI / WSDL / SOAP / REST
1
UDDI
  • 服务的注册和发现，允许提供者把服务描述注册到注册中心
2
WSDL
  • 描述服务的接口和操作：定义输入、输出、交互方式
3
SOAP
  • 不同计算机间通信的消息交换协议，一般是 XML 文件
4
REST
  • 分布式系统架构风格：资源(URL)、表现层(JSON/XML)、HTTP 方法(GET/POST/PUT/DELETE)、无状态、客户端-服务器、统一接口
4ESB 企业服务总线

ESB 是由中间件技术实现的支持 SOA 的基础软件平台，支持异构环境中服务以基于消息和事件驱动的模式交互。交互过程：请求者触发 → 消息标准化 → 发送总线 → 按服务名/接口名查找 → 转发 → 逆向返回，是事件驱动的消息交互而非点对点。

  • 核心功能：位置透明的消息路由寻址、服务注册命名管理、多种消息传递范型（请求/响应、发布/订阅）、多传输协议、多数据格式转换、日志监控。
5SOA 设计原则（8 条）
  • 无状态：调用服务不依赖其他状态/数据。
  • 单一实例：每个服务只提供单一功能，避免冗余。
  • 明确定义的接口：服务定义长期稳定，一旦公布不能随意改，不让使用者看到私有数据。
  • 自包含和模块化：独立部署、版本控制、自我管理恢复。
  • 粗粒度：服务数量不宜太多，靠消息交互而非 RPC。
  • 松耦合：使用者只见接口，位置/实现/状态不可见。
  • 重用能力：服务可重用。
  • 互操作性、兼容和策略声明：策略（安全要求、费用、服务级别）在交互时很重要。
6SOA 设计模式
模式要点
服务注册表模式支持 SOA 治理：服务注册（提供者公布功能）、服务位置（查询符合要求的服务）、服务绑定（利用服务合同开发代码并绑定调用）
企业服务总线模式中间件实现，异构环境服务以消息/事件驱动交互，具有服务质量和可管理性
◆ 费曼

SOA 说人话：一群老系统想互通又不想推倒重来，就加一个「ESB 总机」当接线员，把所有消息先标准统一再转发——这就是 SOA。微服务则是新建一批小而独立的应用，各自管一小块业务，用统一的 REST 直接互调，不设总机。区别就四个字记：「粒度、通信、交付、场景」。三个协议各管一段：UDDI 管登记（注册发现）、WSDL 管说明书（接口）、SOAP 管寄信（消息），REST 则是另一套更轻的架构风格。

▸ 总结

SOA 与微服务四区别：粒度（粗/细）、通信（ESB/统一协议）、交付（兼容/快速）、场景（企业级/互联网）；参考架构六大类＝业务逻辑、控制、连接(ESB)、业务创新优化、开发、IT 服务管理；协议 UDDI 注册发现 / WSDL 描述接口 / SOAP 消息交换 / REST 架构风格；设计原则 8 条（无状态/单一实例/明确接口/自包含/粗粒度/松耦合/重用/互操作）。重点应对选择题和论文。
