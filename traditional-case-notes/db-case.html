▸ 核心要点
1数据库规范化（范式）
范式要求（口诀）
1NF所有字段都是不可分割的原子值（表中不允许有小表）
2NF在 1NF 上，每个非主属性完全依赖候选键（表中不能存在联合主键）
3NF在 2NF 上，非主属性不依赖其它非主属性（不能存在传递依赖）
BCNF3NF 的补充，所有属性都只依赖主键（主属性也不能传递/部分依赖码，除码外无函数关系）
4NF在 3NF 上，一个主键只对应一个多值（如学生-住址-电话的多值依赖需拆表）

独立多值依赖为何违反 4NF（学生信息表（学生ID，住址，电话号码））：

  • 判断链：主键是单字段「学生ID」→ 无部分依赖，满足 2NF；住址/电话互不决定 → 无传递依赖，满足 3NF 甚至 BCNF；但「学生ID →→ 住址」和「学生ID →→ 电话」是两条独立的非平凡多值依赖 → 不满足 4NF。
  • 危害：笛卡尔积冗余——一个学生 2 个住址 × 3 个电话，表里就要存 2×3=6 行（全排列），浪费空间且易产生更新异常。
  • 解法：拆成两张表 (学生ID, 住址) 和 (学生ID, 电话号码)，各自独立多值互不干扰。

口诀：遇到「两个属性各自独立地一对多还塞同一张表」→ 不满足 4NF，拆表解决。

2并发控制 + 封锁协议

并发三大问题：丢失更新（两个事务改同一数据互相覆盖）、不可重复读（一事务重复读两次数据有误）、读脏数据（读到另一事务已修改但随后回滚的数据）。

  • 读脏数据：读到未提交、可能回滚的假数据。例：A 读余额 1000 → B 改 800（未提交）→ A 再读=800（脏）→ B 回滚余额回 1000，A 用 800 决策全错。
  • 不可重复读：同一事务两次读同一行结果不一致（被别人已提交事务改掉）。例：事务 A 第一次读余额 1000 → B 提交改 500 → A 第二次读=500。
  • 区别一句话：脏读是"读到别人没提交会回滚的假数据"，不可重复读是"读到别人已提交的真数据但两次读不一致"。两者都防 → 三级封锁协议（S 锁全程持有）。
  • X 锁（排它锁/写锁）：加 X 锁后只允许本事务读改，其他事务不能加任何锁。
  • S 锁（共享锁/读锁）：加 S 锁后其他事务只能再加 S 锁（可读）不能加 X 锁（不能改）。
封锁协议规则 / 能解决的问题
一级修改前加 X 锁直到事务结束（COMMIT/ROLLBACK）；可防止丢失修改，不能保证可重复读和不读脏数据
二级一级 + 读前加 S 锁、读完即释放；解决丢失更新、读脏数据
三级一级 + 读前加 S 锁、事务结束才释放；解决丢失更新、读脏数据、不可重复读

封锁协议定义：对数据加锁时遵守的一组规则，规定何时加 S 锁/X 锁、锁持有多久才释放，靠它保证并发事务调度正确（等价于串行）。

  • 为什么三级能全解决：写前拿 X 锁且持有到事务结束 → 防丢失更新（第二个事务等锁释放）；读前加 S 锁 → 读不到被 X 锁保护的数据 → 防读脏数据；S 锁持有到事务结束才释放 → 事务内数据不被改 → 防不可重复读（二级"读完即放"就防不住这个）。
  • 口诀：一级锁到提交（防丢更）→ 二级读完即放（再防脏读）→ 三级持锁到底（全防住）。
3主从数据库 + 读写分离

主从数据库架构：一个主服务器复制数据到一个/多个从服务器，写操作（INSERT/UPDATE/DELETE）在主服务器执行后同步到从服务器。特点：数据冗余和读取负载均衡、高可用性、备份恢复。

  • 读写分离：把读操作和写操作分散到不同服务器，主库处理写、从库处理读。优势：提高并发、可水平扩展、降低延迟。
  • 同步复制：写操作须在从库完成复制才能确认（强一致，延迟高）；半同步复制：主库完成即返回成功，但下一写操作前须至少一个从库收到前一操作（折衷）。
  • MVCC（多版本并发控制）：读操作访问一致性时间点快照，不被写锁阻塞。
4数据库分类 + NoSQL
  • 关系型：建立在关系模型上，多张能互相联接的二维行列表格。
  • NoSQL：非关系型，不保证 ACID。特征：易扩展、大数据量、高性能、灵活数据模型、高可用。
  • NewSQL：结合传统 SQL 的强一致/复杂查询 + NoSQL 的可伸缩/高性能/分布式。
NoSQL 类型代表 / 应用
键值对Redis、MemCache；内容缓存、高访问负载、日志；查找快但数据无结构化
文档型CouchDB、MongoDB；Web 应用；表结构可变、无需预定义结构，但查询性能不高
列存储HBase（大数据）、Doris；分布式文件系统；查找快、可扩展强但功能局限
图关系Neo4j、InfoGrid；社交网络、推荐系统；可用图算法但难做分布式集群
5反规范化技术 + 缓存 + ORM

反规范化：规范化设计后，牺牲部分规范化来提高性能。5 种方法：

  • 增加冗余列（多表保留相同列）、增加派生列（可计算生成的列）、重新组表（合并常连接的两表）、水平分割表（按列值分表，用于大表）、垂直分割表（主键+部分列拆表，减少 I/O）。
  • 问题：更新异常、插入异常（数据不一致）。解决：触发器、并发控制、应用程序逻辑（更新频繁用触发器/并发控制，不频繁用应用逻辑）。

Redis vs MemCache：都基于内存、支持 key-value。区别——Redis 支持 list/set/hash 等结构；Redis 内存用完可把久未使用的 value 换到磁盘（MemCache 不能）；Redis 是数据库系统，MemCache 只是简单 K/V 缓存。

ORM：对象关系映射，表→类、记录→对象、字段→属性。优点：降成本、不写 SQL、减代码量；缺点：复杂查询难、性能比直接 SQL 差。

6真题 — 医药销售系统（反规范化 + Redis）
  • 反规范化改造：查询商品信息需同时显示药品+供应商+库存，采用增加冗余列方式。
  • 数据不一致解决：批处理维护、应用逻辑、触发器（本系统实时性要求高，采用触发器）。
  • Redis 热销药品排名：用 ZSet（有序集合） 类型。
  • Redis 与 MySQL 同步：强一致用实时同步（查不到再从 DB 查、更新先改库再设缓存过期）；高并发用异步队列（Kafka）；阿里 canal（监控 binlog 触发更新）；UDP 自定义函数 + 触发器。
◆ 费曼

数据库案例说人话：范式就是给表「减肥去重」——1NF 拆原子值、2NF 消灭部分依赖、3NF 消灭传递依赖、BCNF 连主属性也不放过、4NF 一个键只对一个多值。并发三大坑：丢更新、不可重复读、读脏数据，用一级→二级→三级封锁协议逐个堵上。反规范化反过来「故意加冗余换性能」，但会带来更新/插入异常。Redis 排热销榜用 ZSet，同步 MySQL 最简单就是「先改库、再让缓存过期」。

▸ 总结

范式1NF 原子值 → 2NF 完全依赖 → 3NF 无传递依赖 → BCNF 全依赖主键 → 4NF 单多值；并发问题丢失更新/不可重复读/读脏数据；X 锁=写锁、S 锁=读锁，三级封锁协议逐级增强；NoSQL 四类键值/文档/列存储/图；反规范化 5 法（冗余列/派生列/重组/水平分割/垂直分割）；Redis 排名称 ZSet。重点应对数据库设计类案例分析。
