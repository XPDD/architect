▸ 核心要点
1软件架构风格定义 + 7 种风格对比

软件架构风格：指描述特定软件系统组织方式的惯用模式。组织方式描述了系统的组成构件和构件的组织方式，惯用模式则反映众多系统共有的结构和语义。

风格主要特点 / 优缺点 / 适合领域
管道-过滤器过滤器相对独立；功能模块复用、可维护扩展、有并发性；不适于交互性强的应用，存在关系的数据流须协调
面向对象力争问题空间与软件系统空间结构一致；高模块性、封装、易维护扩充；缺点：增加对象间依赖
事件驱动系统由子系统构成，子系统有主从之分，各有事件收集处理机制；易并发、可扩展、类层次；缺点：削弱计算控制、逻辑复杂
分层风格各层组件形成不同功能级别虚拟机，多层协同且实现透明；逐级抽象、可扩展、支持复用；缺点：层间耦合高的系统难实现
数据共享风格中央数据单元 + 相对独立组件；数据集中以数据为中心；适合专家系统等 AI 领域
解释器风格系统核心是虚拟机，多种操作解释一个句子；适合模式匹配系统与语言编译器
闭环控制风格将控制理论引入软件体系结构，不断测量被控对象；系统中必存在目标作用、信息处理闭环控制过程
2C/S 架构（两层 / 三层）

两层 C/S：客户端和服务器都有处理功能，现不常用。缺点：开发成本高、客户端程序设计复杂、信息内容形式单一、界面风格不一、软件移植/维护/升级困难、新技术难应用、安全性问题、服务器端压力大难复用。

  • 三层 C/S：将处理功能独立出来，表示层在客户机、功能层在应用服务器、数据层在数据库服务器。即把两层 C/S 的数据从服务器独立出来。
  • 优点四点：各层逻辑独立、结构清晰（可维护可扩展）；可灵活选用平台硬件（可升级开放性）；各层可并行开发、各选语言；功能层隔离表示层与数据层（安全管理更合理）。
  • 关键：各层之间的通信效率——要慎重考虑通信方法、频度、数据量，否则硬件再强性能也不高。
3B/S 架构 + 混合架构
  • 三层 B/S：是三层 C/S 的变种，客户端变浏览器、应用服务器变 Web 服务器，又称「0 客户端架构」。不用开发客户端，但缺点：安全性难控制；查询响应速度远低于 C/S（C/S 有本地数据）；数据提交以页面为单位、动态交互性不强。
  • 混合架构风格：内外有别模型（企业内部用 C/S、外部人员用 B/S）；查改有别模型（B/S 查询、C/S 修改）。混合架构实现困难且成本高。
4RIA 富互联网应用
  • RIA：弥补三层 B/S 的问题，是比 HTML 更健壮、有可视化内容的用户接口，本质仍是网站模式。
  • 优点：结合 C/S 反应快交互强 + B/S 传播广；简化改进 B/S 用户交互；数据可缓存在客户端（响应快、往返少）；本质 0 客户端，借助高速网速实现插件本地缓存，典型如小程序。
5MVC / MVP / MVVM 架构
架构核心思想
MVC模型(Model 处理数据逻辑)、视图(View 显示、不处理业务)、控制器(Controller 处理交互、读视图控制输入并发送数据给模型)。好处：管理复杂应用、简化分组开发、易于测试
MVP把 Controller 换成 Presenter，完全切断 View 与 Model 联系。M/V/P 双向通信；View 非常薄（被动视图）、Presenter 非常厚；Presenter 与 View 通过接口交互，可重用
MVVM分离 View 和 Model，实现双向绑定。优点：低耦合、可重用（视图逻辑放 ViewModel）、独立开发、可测试（针对 ViewModel 写测试）

为什么需要 MVP（MVC 的痛点）：

  • MVC 中 View 可直接读取 Model，两者耦合，改一方常牵动另一方；View 还依赖具体 UI 环境，难以单元测试（业务散在 Controller/View，测试要拉起界面）。
  • MVP 解决：View 变被动视图（很薄，只显示 + 转发事件），Presenter 变厚（交互逻辑/读写 Model 全在 Presenter），通过 View 接口反向调 View。结果：View 与 Model 完全解耦，Presenter 可用 Mock View 独立单测、可重用、可替换。
主流框架 / 技术所属模式
VueMVVM（v-model 双向绑定，内置 ViewModel）
React纯 View 层 + 单向数据流（配 Redux/Zustand 属 Flux 系，既非 MVP 也非 MVVM）
AngularMVVM 倾向（内置数据绑定）
Android 原生常用 MVP / MVVM（Google 后推 ViewModel+LiveData/Flow，Compose 走单向数据流）

MVP 最小示例（Kotlin / Android）：

// View 接口：Presenter 只依赖接口，不依赖具体 Activity
interface LoginView {
    fun getUsername(): String
    fun showError(msg: String)
    fun onLoginSuccess()
}

// Presenter：逻辑全在这，Model 与 View 互不相识
class LoginPresenter(private val view: LoginView, private val model: UserModel) {
    fun onLoginClicked() {
        if (view.getUsername().isEmpty()) view.showError("用户名不能为空")
        else if (model.login(view.getUsername(), "pwd")) view.onLoginSuccess()
        else view.showError("用户名或密码错误")
    }
}

// 单测：Mock 掉 View，不用模拟器即可跑
val mockView = mock(LoginView::class)
LoginPresenter(mockView, UserModel()).onLoginClicked()
verify(mockView).showError("用户名不能为空")
6真题 — 层次架构（文化用品商城系统）

决定系统架构设计的非功能性需求四类：

  • 操作性需求：与用户操作使用系统相关的需求（如界面个性化定制 a、支持主流标准 b）。
  • 性能需求：响应时间、吞吐量、准确性、有效性、资源利用率（可靠性、可用性也归此类）；如响应时间 c、故障诊断 d、数据缓存 f。
  • 安全性需求：向合法用户提供服务并阻止非授权访问；如密码加密传输 e、超时重新登录 g。
  • 文化需求：带文化背景因素的需求；如多语言选择 h。

瘦客户端 vs 胖客户端：瘦客户端把业务逻辑从客户端放到服务器（故障修复只改服务器、可加密传输、可集群支持），但难做大数据缓存；胖客户端运算能力强、易做缓存但难加密传输、更新所有客户端工作量大。

7真题 — 架构风格选择（脚本语言 IDE）

结论：对脚本语言 IDE（编辑/语法检查/解释/调试），王工主张管道-过滤器，李工主张以数据存储为中心，最终采用李工方案。原因：

  • 交互方式：用户交互式编辑/解释/调试，数据存储为中心支持交互式处理，管道-过滤器支持有限。
  • 扩展性：数据存储为中心以数据格式解耦各功能依赖、可灵活定义功能顺序；管道-过滤器对处理逻辑关系灵活定义较差。
  • 数据管理：需支持多种数据类型（脚本/语法树/可视化模型/调试信息）及格式转换，中心存储器能表示多种格式，管道-过滤器数据格式转换灵活性差。

配套：可视化界面编排 → 解释器风格（定义语言语法语义、写解释器、生成脚本程序）；代码自动定位 → 隐式调用（事件驱动）风格（定义断点命中事件、事件注册表、监听并调用定位函数）。

◆ 费曼

架构风格说人话：就是「搭系统的固定套路」——管道-过滤器像流水线（一节节过滤）、数据共享像中央黑板（大家都读写一块数据）、事件驱动像广播（谁订阅谁响应）、分层像千层饼、解释器像翻译机。C/S 是「胖客户端自己算」，B/S 是「瘦到只剩浏览器」（0 客户端）。MVC 三兄弟记住演进：MVC（控制器传话，V/M 仍可直连）→ MVP（Presenter 切断 View 和 Model，V 变被动薄壳，可 Mock 单测）→ MVVM（双向绑定自动同步）。框架归属：Vue=MVVM、React=纯 View+单向数据流、Android 常用 MVP/MVVM。

▸ 总结

软件架构风格＝描述系统组织方式的惯用模式；常见 7 种：管道-过滤器、面向对象、事件驱动、分层、数据共享、解释器、闭环控制；两层 C/S 缺点多，三层 C/S 把数据/功能/表示分离；三层 B/S＝0 客户端但安全性/速度差；混合架构有内外有别、查改有别两模型；MVC→MVP→MVVM 演进，MVP 因「V/M 直连耦合、View 难测试」而生（Presenter 中介 + View 接口可 Mock 单测），Vue=MVVM、React=纯 View、Android 常用 MVP/MVVM；非功能需求分操作性/性能/安全性/文化四类。重点应对架构风格选择类案例分析。
