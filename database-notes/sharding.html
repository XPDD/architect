▸ 核心要点
1先把题目翻译成大白话

把订单库想象成一本又厚又大的账本：

  • 单表 8 亿行＝这本账有 8 亿条记录，翻一次很慢；
  • 日增 600 万行＝每天还在往里加 600 万条，越来越厚；
  • 写入锁竞争＝很多人同时要改账本，互相"抢笔"排队；
  • CPU 飙高、查询超时＝账本太重，翻页和写入都把机器累垮。

结论：一本账本扛不动了，得拆成很多本小账本——这就是"分库分表"。为便于整理，先记住一个主线：拆开（分片）→ 分头找（路由/查询）→ 各自编号不重复（分布式 ID）→ 老数据搬走（归档/统计）。

2名词速查（不懂的词看这里）
分库分表把一张超大表 / 一个超大库，按规则切成很多小库、小表，把压力分摊开
分片切出来的其中一个小库或小表（也叫 shard）
分片键决定"一条数据该放哪个分片"的那个字段；本题选 用户 ID
路由根据分片键算出"这条数据该去哪个分片"的过程
全分片广播一次查询把所有分片都问一遍，很慢（要尽量避免）
分布式 ID分表后每张表自增主键会重复，需要一个全局唯一、不重复的编号
雪花算法用"时间戳＋机器号＋序号"拼出一个全局唯一、且大致递增的 ID
号段模式一次从数据库领一批 ID（如 1000 个）慢慢发，性能高但依赖发号中心
UUID本地随机生成的长字符串，全局唯一但无序，做主键性能差
binlog数据库的"变更流水日志"，记录每一次增、删、改
订阅同步像订阅消息一样读 binlog，把数据实时"搬"到别处（如 ES）
宽表把常用字段拼成一张很宽的大表，专门给查询/检索用
ESElasticsearch，专门做"搜索＋组合筛选＋排序分页"的搜索引擎
读写分离主库负责写、从库负责读，分担压力
强一致 / 最终一致强一致＝下单成功就一定落库、绝不丢；最终一致＝允许暂时不同步，过一会儿自动对齐（如同步到 ES）
热 / 温 / 冷数据热＝最近常查的；温＝几个月前的；冷＝很久不动的
归档库把老数据搬到便宜的存储里，给在线库"减负"
汇总层 / 数仓预先算好的统计结果，专门给报表用
3分库分表到底是什么（两种切法）
  • 垂直拆分：按业务/字段分——把订单、用户、商品拆到不同库。像把一本大账分成"订单账、用户账、商品账"。
  • 水平拆分：按行分——同一张订单表，按规则拆成多张结构一样的小表。本题做的就是水平拆分。
  • 分片键：水平拆分按哪个字段切？本题选用户 ID。

4分片键为什么选"用户 ID"？以及它带来的三个麻烦

选用户 ID 的理由：用户最常查的是"我的订单"，按用户 ID 分片后，同一个用户的订单都落在同一个分片，一查就命中，很快。

但商家侧会出问题：商家要按"订单号 / 时间 / 状态"组合查，这些条件跟用户 ID 没直接关系，就找不到该查哪个分片，只能把所有分片都问一遍（全分片广播），又慢又乱。

分片后一共冒出三个大麻烦：

麻烦通俗解释应对方向
① 跨分片查询一条查询用不上分片键，就得翻遍所有分片订单号带路由 / 建"订单号→用户ID"映射表 / 商家查询走 ES 宽表
② 分布式 ID每张分表都自增，会撞号（出现重复订单号）用全局唯一的分布式 ID（见第 5 节）
③ 路由与聚合得知道去哪写、去哪读；真要聚合还得合并各分片结果路由规则 + 并行查询 + 网关归并排序
5分布式 ID：三种方案怎么选
方案大白话优点缺点
数据库号段一次从数据库领一批号（如 1000 个）慢慢发性能高、趋势递增便于索引依赖发号中心；多实例要协调
雪花算法时间戳＋机器号＋序号 拼出来的号无中心依赖、趋势递增、性能好要处理"时钟回拨"和机器号分配
UUID本地随机生成的长字符串完全本地、无中心无序，主键索引性能差；太长

本题选雪花算法，还可在订单号前缀里带上业务/分片信息，方便按订单号直接路由。

6跨分片查询怎么破（四条路，别硬广播）

② 按用户查
→

④ 确实要跨片聚合
→
各分片并行查 → 网关归并排序 → 游标翻页
7数据越积越多：热 / 温 / 统计 三层
◆ 实库 + 归档库 + 汇总层
热数据 · 近 3 个月订单
留在在线分库分表库，扛高频读写
↓ 凌晨低峰批量归档
温数据 · 3～24 个月
搬到归档库 / 冷存储，低频按需查
↓ 每日/每月定时任务
统计数据 · 汇总层 / 数仓
StarRocks、ClickHouse 等，供运营报表
8全景流程（把它串起来）
◆ 下单 → 同步 → 查询 → 归档
① 下单（写）
↓ 雪花算法生成订单号 → 按用户ID路由 → 写入对应分片（强一致、事务保证不丢）
② 变更日志 binlog
↓ 订阅同步（如 Canal）实时搬运
③ 写入 ES / 宽表（供商家组合查、最终一致）
↓
④ 查询分流：按订单号/用户直查分片；商家组合查走 ES
↓ 数据变老
⑤ 归档到温/冷存储；统计任务汇总到数仓 → 报表
9回到题目四小问（要点速记）
问题要点
问题1 分片键选用户 ID（高频"我的订单"、局部性好）；商家按订单号/时间/状态查会全分片广播；解法：订单号嵌路由、映射表、另建 ES 宽表
问题2 分布式 ID对比号段/雪花/UUID；本场景选雪花算法（可加业务前缀便于订单号路由）
问题3 全链路查询订单号直查、用户命中单分片、商家组走 ES、跨片聚合用"并行查＋归并排序＋游标翻页"
问题4 分层报表热（近3月，在线库）／温（3～24月，归档冷存）／统计（定时汇总到数仓 OLAP）
◆ 费曼

分库分表说人话：一个图书馆只有一本 8 亿页的目录，找一本书要把整本翻完，写新书还得抢同一支笔——当然卡。于是把它拆成好几本分册（分片），按"借书人编号"决定去第几册找（分片键）。这样"我的借阅记录"总在同一册，很快。但麻烦也来了：管理人员要按"书名/日期"查，就不知道在哪一册，只能翻遍所有册（全分片广播），所以另做一本搜索索引（ES）专门给人组合查。拆开之后每册自己编号会撞号，于是统一用雪花算法发全球唯一的号。老记录越来越多，就把旧的搬去仓库（归档），报表数据提前算好放汇总层。一句话：拆开提速，但要用"路由 + 全局ID + 搜索索引 + 归档"来收尾。

▸ 总结

单表太大 → 水平分库分表（按用户ID分片）；分片带来三麻烦＝跨分片查询、分布式ID、路由聚合；跨分片别硬广播，用订单号嵌路由 + ES 宽表（binlog 同步）+ 并行归并；全局唯一 ID 选雪花算法；老数据按热（在线库）/温（归档）/统计（数仓）分层。主线：分片 → 路由/查询 → 全局ID → 归档统计。
