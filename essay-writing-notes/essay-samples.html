1范文1：论层次架构（银行远期结售汇 · 三层C/S）

项目：2019年1月主持远期结售汇系统，综合业务系统子系统。选 三层C/S结构：字符终端（表示层）→ CICS TRANSACTION SERVER（中间层）→ DB2 UDB7.1（数据层）。

✓
三层选型理由
  • 表示层：字符终端 CITE（VB开发）——比 IBM 图形终端响应更快
  • 中间层：IBM CTS——兼容原大型机体系、保护投资、缩短开发周期
  • 数据层：DB2 UDB7.1——大型事务处理出色、延续技术连续性
✓
两大难点解决
  • CICS SWITCH 组：一组相同 CTS 消除单点故障 + 数据库连接池提速
  • 并行批量：OPC 统一提交 + DB2 PARTITION 分片并行，支持断点重提

结尾：总结不足 + 改进（范例写法）

  • 不足1：负载均衡算法过于简单 → 改为基于统计的概率分配
  • 不足2：并行批量设计不严谨致资源冲突 → 调整作业顺序 / DB2 共享锁 / 制定作业提交规范
  • 评价：结构完整、技术细节扎实，是"问题→方案→结果"的典范
2范文2：论面向服务架构（水利大坝施工质量监控 · SOA）

项目：2016年8月参与胶凝砂砾石坝施工质量监控系统，担任系统分析师。功能：采料/运料/拌合/碾压/温湿度监控。采用 SOA 企业应用集成。

服务提供者

→
服务注册中心
UDDI 发布 · 独立性与松耦合
→
服务请求者
Web Service 调用

写法亮点 + 失误

  • 亮点：拆出两个核心服务——标准拌合对比服务（预留标准拌合比输入接口）、碾压轨迹生成服务（预留 GPS/超宽带两种数据格式接口）
  • 亮点：服务数量少（粗粒度）、减少服务间通信，WSDL 描述 + UDDI 发布
  • 失误：正文只写业务+SOA概念，技术点太少——"尽量把技术加上去，更容易得分"
  • 失误：结尾用大段介绍 SOA 优势替代"项目效果+不足"，且优势未结合项目——不推荐
3范文3：论面向对象建模（数据安全访问平台 · UML）

项目：2018年"数据安全访问平台"，数据中心二期。目标：建立统一数据访问接口、规范并强制审计数据库访问行为。采用 精简 RUP + UML + Rational Rose。

①
四种图的应用
  • 用例图：描述用户与系统交互；55个用例，仅5个关键高风险用例细化（前置/后置条件、基本流、扩展流）
  • 类图：描述核心概念（逻辑连接、用户、受限角色、认证SQL等）
  • 部署图：描述网络部署；监控子系统需接入核心交换机镜像端口
  • 活动图：描述应用流程；泳道表达应用开发方与信息中心交互
✗
讲师指出的不足
  • 部署图/活动图应分开写，内容少可直接去掉
  • 类图写太少、只在摆概念——应按"定义概念类→识别类关系→添加职责"结合项目写
  • 类图对应关系写错了
  • Word 文档与模型靠截图手工维护一致性，繁琐易错（应引入 Soda 工具）
4范文4：论软件系统架构风格（公交车联网一体化）★最好的一篇

项目：2016年浙江某市公交"车联网一体化"，担任架构师。底层 CAN 数据协议达 86 种，4人架构小组，7个月完成。

①
底层 · 虚拟机风格·解释器
  • 解决 86 种 CAN 协议兼容：XML 映射"协议链-数据帧-数据字节-数据位"4层结构
  • jdom + Java反射动态生成对象，基于可变模板的解释器，模板可热部署
  • 协议变更只改模板文件，86 个描述文件搞定全部协议
②
中间层 · 独立构件·隐式调用
  • ActiveMQ 消息发布/订阅，解耦各 Web 应用（调度/机护/电池监控）
  • Spring 配置化管理队列，主题可随时增改、监听组合灵活

应用层 · B/S 风格 + 讲师的"范文级"评价

  • B/S 解决公交行业"推广难、维护难"：子公司遍布全市、内网+APN专网，C/S 更新要跑全城；用 HTML5+前端缓存+WebSocket 补交互
  • 评价：正文写得很好——正好3段、每段先一句话介绍风格特点再结合项目问题讲解
  • 评价：每段都加入具体技术点和设计实现过程，结尾有上线效果+客户评价+不足及改进（新购PC、服务器冗余+心跳）
5范文5：论软件系统架构评估（漏洞挖掘系统 · ATAM）

项目：2016年国家某安全中心漏洞挖掘系统，担任系统架构设计师 + 评估小组负责人。架构采用 SOA，评估采用 基于场景的 ATAM。

①
质量属性（前4为核心）
  • 性能：系统响应能力（响应时间）
  • 可用性：正常运行比例（故障间隔/恢复速度）
  • 可修改性：以较高性价比变更系统的能力
  • 安全性：向合法用户服务、拒绝非授权
②
评估方法选型
  • 问卷调查：主观，不适合
  • 度量：客观但需对架构精确了解，不适合
  • 基于场景：对系统中等了解即可 → 选用；分 ATAM / SAAM / CBAM
描述介绍
介绍ATAM+商业动机+架构
→
调查分析
收集场景·质量效应树
→
测试
定优先级·双机热备/集群
→
报告
风险点/敏感点/权衡点文档

ATAM 输出 + 点评

  • 风险点：IP 不能实时捕获丢漏洞信息；消息处理超12小时积压
  • 敏感点：加密级别、漏洞规则修改；权衡点：规则严格度↔准确率/性能、加密↔安全/性能
  • 测试阶段优先级：可用性最高 > 性能 > 可修改性/安全性；双机热备、集群部署、RAID5、非对称加密+信息摘要
  • 评价：评估方法选型→四阶段结合项目描述，全程无误；结尾有上线效果+客户评价，字数够可不写不足
6范文6：论微服务架构及其应用（在线问诊互联网医院）

项目：2019年3月"在线问诊互联网医院平台"，担任架构师。核心功能：用户信息、病历、推荐处方、药品配送。旧单体已无法适应快速扩张 → 微服务改造。

①
微服务拆分（职责单一）
  • 边界明确、不重复开发；每个服务独立数据库
  • 基础服务层：网关/认证/权限/用户/IM/支付
  • 业务服务层：诊疗/订单/处方/病历；工具服务层：定时/文件/日志/分布式事务
  • 认证与用户分离：认证宕机不影响用户服务，容错更高
②
治理 + 限流熔断
  • 治理：Nacos 注册中心（服务名查 IP/端口、30秒心跳、异常剔除）+ 配置中心（动态配置免发版）
  • 限流熔断：Hystrix 断路器，节点故障返回备选响应，防雪崩

结尾

  • 亮点：上线效果量化（4W+医生注册、百万患者、按服务发版、水平扩容）
  • 不足：没展开"不足和解决措施"，只写了微服务带来的好处——"还是没有写不足之处和解决措施好"
7范文7：论云原生架构及其应用（OJ 程序在线评测系统）

项目：2019年《程序在线评测比赛考试系统》(OJ)，联合高校研发。核心：代码在线提交自动评测。担任架构师，采用 Spring Cloud + Docker 云原生。

①
前端 Web 服务
  • 前置 Nginx 负载均衡（最小连接法）+ 前端网站 Nginx 集群
  • 反向代理路由模式，内外网逻辑隔离
②
平台保障服务
  • API 路由网关 + Eureka 服务注册中心（三大角色）+ 监控平台
  • 两两互相注册，网关多实例注册，保障高可靠

业务服务 + 场景问题（加分项）

  • 业务服务：题库/评测机/考试/比赛/抄袭判定，Docker 容器打包，多实例集群（评测机/抄袭判定压力大）
  • 场景1 跨域：前后端分离 Ajax 受限 → Spring Boot CORS 解决
  • 场景2 评测机宕机：大量不安全代码致全部宕机 → 心跳+快照回滚+机器学习预判断，10秒自动重置
  • 最大败笔：整个过程几乎没写"云原生架构"的内容，也没突出用云原生后的好处
  • 第一个问题（跨域）太低级，不该是架构师考虑的问题；结尾记得呼应题目点题
◆ 费曼

七篇范文就是七套"答题模板"。 记住三条铁律：① 每段都要"先一句话介绍概念/风格特点，再结合项目讲问题→方案→技术→结果"（范文4 是最佳示范）；② 正文技术点要给足、给具体（范文2 吃了只写概念的亏）；③ 结尾三件套：量化上线效果 + 客户评价 + 不足解决思路（范文6 缺不足被点名）。再记住两个反面教材：范文7 最大的坑是"通篇没讲题目的'云原生'"，说明论文必须紧扣题眼；范文2 的教训是结尾别写成"概念宣讲会"，要回到自己项目。

▸ 总结

七篇范文 = 七套架构论文模板：层次C/S（三层选型+并行批量/CICS集群）、SOA（提供者-注册中心-请求者，正文要多写技术）、UML（用例/类/部署/活动图，类图要"定义概念类→识别关系→添加职责"）、架构风格（解释器/隐式调用/B/S 三层对应，范文级示范）、架构评估（质量属性+方法选型+ATAM四阶段）、微服务（职责单一拆分+Nacos治理+Hystrix熔断）、云原生（Nginx集群+Eureka+Docker容器，切忌脱离题眼）。通用套路=概念一句话→项目问题→方案取舍→具体技术→量化结果。
