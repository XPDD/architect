案例 1
电商「商品详情」接口——缓存三兄弟
某电商商品详情接口逻辑：先查 Redis → 未命中查 MySQL → 查到写回 Redis。上线后出现三种情况：A) 黑客用脚本批量请求不存在的商品 ID（如 9999999），Redis 无缓存，所有请求直达 MySQL 打爆 DB；B) 一款秒杀爆款商品的缓存正好过期，瞬间 10 万并发请求冲 DB 导致连接超时；C) 为保证数据新鲜，所有生鲜商品缓存都设「0 点整过期」，0 点秒杀时几千万请求同时打到 MySQL。
问题 1分别判断 A、B、C 各属于哪种缓存问题？
问题 2分别说明对应的解决方案。
参考答案

A＝缓存穿透（查询不存在的数据、直达 DB）→ ①缓存空对象（设短期过期）②布隆过滤器前置拦截（元素肯定不存在直接返回，有误判≈5%、不支持删除）。

B＝缓存击穿（单个热点 key 过期、高并发打 DB）→ ①互斥锁（分布式锁，强一致但性能差）②逻辑过期（先把过期时间字段存进缓存、不给 key 设真实过期，另开线程异步更新，高可用但数据可能非最新）。

C＝缓存雪崩（大量 key 同时过期或 Redis 宕机）→ ①过期时间加随机值（如 10±2 秒）②多级缓存（本地 Caffeine + Redis）③限流降级（Nginx/Gateway，作为保底）④集群高可用（哨兵/分片）规避单节点宕机。

口诀：穿透无中生有、击穿独木难支、雪崩全军覆没。

案例 2
抢优惠券库存——防超卖
某抢券接口并发扣减优惠券库存：先 get 库存 → 判断 >0 → 减 1 → set 回写。上线后发现库存被扣成负数（超卖）。开发组先加 Java synchronized 仍没解决。
问题 1为什么 synchronized 解决不了？
问题 2Redis 层如何防止超卖？
问题 3悲观锁和乐观锁方案分别怎么落地？
参考答案

问题 1：synchronized 只在本机 JVM 内生效，服务集群部署后多个节点各自加锁互不感知，依旧会并发扣减导致超卖。

问题 2：利用 Redis setnx 实现分布式锁（SET lock value NX EX 10），或用 incr/decr 原子指令 / Lua 脚本保证「读取-判断-扣减」原子执行，杜绝超卖。

问题 3：悲观锁＝抢券接口加 Redisson 排他锁（先锁后干、强一致、适合写多高冲突），底层 setnx+Lua；乐观锁＝WATCH + MULTI/EXEC（提交时校验库存是否被改、被改则重试，性能高、适合读多写少，如文章点赞）。口诀：悲观先锁后干、乐观放手去干提交把关。

案例 3
高并发秒杀系统架构设计
某平台要做「618 秒杀」：一款 9.9 元爆款耳机，需要在短时间内承受百万级并发抢购，同时要保证不超卖、不过度压垮数据库。
问题请给出秒杀系统的核心处理链路，并说明每一步对应的 Redis 能力。
参考答案

核心链路（论文/面试常用闭环）：热点预热 → Redis 限流 → 分布式锁放行 → MQ 削峰 → 落库 → Canal 异步同步缓存。

  • 预热：提前把秒杀商品加载进 Redis 缓存（防击穿）。
  • 限流：网关层 Nginx 限流 + 业务层 Redis 限流（固定窗口 INCR+EXPIRE / 滑动窗口 Zset / 令牌桶 / 漏桶），把超量请求挡在门外。
  • 分布式锁：setnx/Redisson 只放一个请求真正扣库存，防超卖。
  • MQ 削峰：把订单写入 Kafka/RabbitMQ 排队慢慢消费，保护 DB。
  • 落库：消费端最终写 MySQL。
  • Canal 同步：监听 MySQL binlog 自动更新缓存，保证最终一致。
案例 4
Redis 与 MySQL 双写一致性
某司用 Redis 缓存 + MySQL 落库。两块业务：①文章热点数据（允许秒级延迟）②抢券库存（必须实时强一致）。
问题 1两套业务分别应采用什么同步方案？
问题 2为什么不用「延迟双删」？
参考答案

问题 1：①允许延迟（文章热点）→ 异步方案：基于 MQ 更新（改完 DB 发消息、消费者更新缓存、有重试兜底），或 Canal 监听 MySQL binlog（伪装成从节点读取 binlog 自动更新缓存，无侵入、实时性高、一致性最好）。②强一致（抢券库存）→ Redisson 读写锁：读加共享锁（读读不互斥、读写互斥）、写加排他锁（全互斥），保证写数据时其他线程读不到脏数据；读写须用同一把锁。

问题 2：延迟双删（先删缓存→改 DB→延迟几秒再删一次）的延迟时长不好确定，且延迟期间可能读到旧数据回写，不能保证强一致性，所以强一致场景不采用。

补充：强一致场景干脆不用缓存直接查库；最终一致仅适用于接受短期不一致的业务。

案例 5
系统要求「数据不能丢 + 快速恢复」
某订单计数系统重启后不能丢失数据，同时要求宕机后能尽快恢复服务。领导问 DBA 该怎么配置 Redis 持久化。
问题请给出持久化配置方案并说明理由。
参考答案

采用 RDB + AOF 混合持久化（最佳实践）：

  • 开启 AOF（appendonly yes），设 appendfsync everysec 每秒刷盘——性能与安全兼顾，最多丢 1 秒数据。
  • 同时开启 RDB（如 save 900 1）——用于快速全量恢复（RDB 是二进制快照、体积小恢复快）。
  • 定期执行 BGREWRITEAOF 重写 AOF，避免文件过大。
  • 重要业务配主从复制：从节点开 AOF、主节点用 RDB 减少性能开销。

理由：RDB 恢复快但可能丢数据（快照间隔之外），AOF 几乎不丢但恢复慢；混合（4.0+）＝AOF 前半段 RDB 全量 + 后半段增量日志，兼得快速恢复与低丢失。

案例 6
Redis 响应变慢排查
某接口调用 Redis 平时 <10ms，最近经常超过 100ms 甚至秒级，用户反馈卡顿。架构师准备排查。
问题请按顺序给出排查思路。
参考答案
  • 先定基线：用 redis-cli 测当前环境基线性能（服务器无压力、无干扰时的性能）。
  • 排除外部因素：测响应速度，排除网络问题（跨机房、带宽不足）和客户端连接数过多。
  • 慢查询：排查复杂度过高的命令，用慢查询日志定位。
  • 大量 key 同时过期：主线程长时间阻塞 → 给过期时间加随机数避免同时删除。
  • bigkey：用 scan 扫描大 key，避免写入 bigkey。
  • AOF 重写/fsync 阻塞：每写命令同步等 fsync 会阻塞主线程 → 允许时改 appendfsync no 或 no-appendfsync-on-rewrite yes，最好用 SSD 存放 AOF。
  • 另注意：keys * 生产禁用（阻塞主线程）。
案例 7
单节点内存不足 / 数据量大
某库有 1000 万条数据，Redis 只能缓存 20 万条；同时单节点 Redis 内存持续告警，说内存快满了，写请求开始报 OOM。
问题 1如何保证缓存里留下的都是热点数据？
问题 2内存满了会发生什么？怎么选淘汰策略？
参考答案

问题 1：用 allkeys-lru 淘汰策略——把最近最少使用的淘汰掉，留下的都是经常访问的热点数据。LFU（按访问频率）也可用于有明确冷热/数据可重建的场景。

问题 2：看淘汰策略。默认 noeviction 时内存不足写请求直接报错（OOM）、读不受影响。常用选择：volatile-lru（淘汰过期键中最久未用，90% 生产场景、保留核心永久数据）、allkeys-lru（纯缓存、数据可重建）。若单节点 超 10G 内存，通常给不同服务分配独立主从节点，尽量不做分片（维护麻烦、耗网络带宽、不能用 Lua 和事务）。

案例 8
集群选型与哨兵脑裂
业务 A：1 主 1 从、读多写少，要自动故障转移；业务 B：海量数据 + 高并发写。某晚哨兵集群网络分区，出现两个 master，恢复后旧 master 大量数据丢失。
问题 1业务 A、B 各适合哪种集群方案？
问题 2「脑裂」怎么发生、如何防范？
参考答案

问题 1：业务 A（读多写少、要自动故障转移）→ 主从 + 哨兵；业务 B（海量数据、高并发写）→ 分片集群（Cluster）（多主多从 + 16384 个哈希槽，CRC16 取模分片，解决存储和写瓶颈）。

问题 2：脑裂＝主节点、从节点、sentinel 处于不同网络分区，sentinel 心跳感知不到 master 就通过选举把某个 slave 提升为新 master，导致两个 master；客户端仍往旧 master 写、新 master 无法同步；网络恢复后哨兵把旧 master 降为 slave 再同步，造成大量数据丢失。防范：配置最少从节点数量（达不到就拒绝写）+缩短主从同步延迟时间（达不到要求拒绝请求）。

案例 9
热点 Key 与大 Key（bigkey）治理
①某秒杀商品 key 被超高并发访问，单节点压力巨大，服务报警；②某用户的积分列表 hash 非常大，读写都带来阻塞、内存分配不均。
问题分别怎么治理两类问题？
参考答案

热点 Key（某 key 被超高并发访问、单节点压力大）→ 二级缓存（本地缓存承接）、key 分片加后缀分散（拆成 key_0、key_1…）、热点识别 + 预热。

大 Key（bigkey）（大 value、阻塞/内存不均/迁移慢）→ 拆分大结构、压缩序列化、避免大字符串、慎用 HGETALL 等一次性取大对象的命令；用 scan 扫描发现 bigkey。

案例 10
防缓存穿透：空值缓存 vs 布隆过滤器
某接口上线后遭到一批「不存在 ID」的恶意请求，直接打爆 DB。团队讨论用「缓存空值」还是「布隆过滤器」来挡。
问题两种方案各有什么优缺点？怎么选？
参考答案

缓存空对象：查询返回空也缓存（{key:1, value:null}）、设短过期。优点简单易实现；缺点消耗内存、可能不一致（大量不存在的 key 都被缓存）。

布隆过滤器：初始化大型位数组（0/1），元素经 3 次 hash 模数组长度置 1，查询看对应位；应用层前置拦截，元素肯定不存在直接返回、不查 Redis/DB。优点内存占用少、无多余 key；缺点实现复杂、存在误判（一般 ≤5%）、不支持删除。

选型：明显是恶意攻击/大量不存在的 key → 用布隆过滤器（省内存、前置拦截）；简单/低频场景 → 用缓存空值（快）。
