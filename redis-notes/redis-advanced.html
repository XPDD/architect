▸ 核心要点
1Redis 事务 + 乐观锁/悲观锁

为什么需要事务：Redis 单线程单命令天然原子，但多条命令组合若被其他客户端插入就无法保证原子性。事务把多条命令打包一次性执行，期间不被插入。

  • MULTI（开启事务，命令排队）、EXEC（执行队列全部命令，不保证经典 ACID 隔离）、DISCARD（取消事务清空队列）、WATCH（监听 key，乐观锁——被改则 EXEC 失败返回 nil）。
  • 注意：Redis 事务不完全等于关系型事务——不保证回滚和隔离，核心是"打包执行 + WATCH 实现乐观并发控制"。
维度悲观锁乐观锁
时机操作前加锁（阻塞）提交时校验（非阻塞）
冲突观点冲突大概率发生（先锁后干）冲突小概率（放手去干）
适用写多强一致（秒杀扣减）读多写少（计数器）
Redis 实现setnx / Redisson 排他锁WATCH + MULTI
2CAP 定理 + BASE 理论 + 一致性哈希
  • CAP：一致性(C)/可用性(A)/分区容错(P) 三者不可兼得，网络分区不可避免，实际 CP 或 AP 二选一。CP（ZooKeeper/etcd/银行转账）；AP（Redis、购物车、缓存场景——最终一致）。
  • BASE：基本可用 + 软状态 + 最终一致，是 AP 的延伸，也是"缓存允许短暂不一致"的理论依据。
  • 一致性哈希：哈希环 + 数据顺时针找最近节点；节点增减仅影响邻近一小段；数据倾斜用虚拟节点分散；代表 Memcached 集群。与哈希槽（Cluster 用 CRC16%16384、槽重新分配）对比。
3缓存读写策略（4 种）
策略工作方式特点
Cache-Aside（旁路）业务代码负责读/写缓存，DB 更新后删缓存最常用、灵活（双写一致方案即此类）
Read-Through缓存组件负责从 DB 读并回填业务"读缓存"更简洁
Write-Through写时先写缓存再同步写 DB缓存与 DB 强同步、偏慢
Write-Behind先写缓存，异步批量落 DB性能高、有丢失风险

Redis vs MemCache 六维度：①能存啥：MemCache 只认字符串，Redis 支持 Hash/List/Set/ZSet；②数据会不会丢：MemCache 纯内存重启就没了，Redis 支持持久化；③高可用：MemCache 无原生高可用，Redis 支持主从/哨兵/集群；④并发安全：Redis 单指令原子 + Lua 脚本，防超卖；⑤内存管理：MemCache 预分配易碎片，Redis 动态管理 + LRU/LFU 淘汰；⑥性能：简单场景相近，复杂查排行榜 Redis 快 10 倍。

4限流算法 + 热点/大 Key

四种限流算法：固定窗口（单位时间计数到上限拒绝，简单但临界点突刺）；滑动窗口（Zset 记时间戳统计窗口内请求，更平滑）；令牌桶（匀速放令牌，突发可短暂超过）；漏桶（匀速流出、超出丢弃，严格削峰）。Redis 落地：固定窗口 INCR key + EXPIRE key N；滑动窗口用 Zset；复杂限流用 Lua 脚本保证原子性。

  • 热点 Key：某 key 被超高并发访问（秒杀商品）→ 二级缓存、key 分片加后缀分散、热点识别+预热。
  • 大 Key（bigkey）：大 value（大 list/hash）导致阻塞、内存不均、迁移慢 → 拆分、压缩序列化、避免大字符串、慎用 HGETALL。
5多级缓存 + MQ 选型 + 秒杀串讲

多级缓存架构：CDN（静态资源）→ Nginx（页面缓存）→ 本地缓存 Caffeine（单机最快）→ Redis（分布式共享）→ 数据库（最终源）；一级失效逐级降级，缓解缓存雪崩。

  • Redis 做 MQ vs 专业 MQ：轻业务用 Redis（List/Stream，blpop 出队、延迟低、简单异步）；重业务（可靠投递、削峰、海量吞吐）用 Kafka/RabbitMQ。Redis 可靠性一般，Kafka 高吞吐多副本。
  • 秒杀架构串讲：热点预热 → Redis 限流 → 分布式锁放行 → MQ 削峰 → 落库 → Canal 异步同步缓存，形成闭环。
◆ 费曼

Redis 进阶说人话：事务就是把多条命令"装进一个盒子一起发"（MULTI…EXEC），WATCH 是乐观锁"先改后看有没有人动过"，悲观锁则"先锁住再改"（setnx/Redisson）。CAP 三选二（网络分区逃不掉，只能 CP 或 AP），BASE 就是"反正最终会一致"给缓存短暂不一致当理论依据。限流四种：固定窗口（一秒一刀）、滑动窗口（连续看）、令牌桶（匀速发牌可突袭）、漏桶（匀速倒水超了就泼）。秒杀一条龙：预热→限流→锁→MQ 削峰→落库→Canal 同步。

▸ 总结

Redis 事务MULTI/EXEC/DISCARD/WATCH，不等于关系型事务；悲观锁 setnx（先锁后干）vs 乐观锁 WATCH+MULTI（提交把关）；CAP（CP 选 ZooKeeper、AP 选 Redis）+ BASE（最终一致）+ 一致性哈希（哈希环+虚拟节点）；缓存读写 4 策略Cache-Aside 最常用；限流 4 算法 + 热点/大 Key 治理 + 多级缓存 CDN→Nginx→Caffeine→Redis→DB；秒杀串讲是论文好素材。
