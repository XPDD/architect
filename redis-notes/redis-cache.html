▸ 核心要点
1缓存穿透

定义：恶意请求大量不存在的 Key，缓存未命中后所有请求直达数据库（MySQL 查不到也不会写入缓存），导致数据库压力激增甚至崩溃。这是"查询不存在的数据"，大概率遭攻击。

  • 方案 1：缓存空对象——查询返回空也缓存（{key:1, value:null}），设短过期时间。优点简单，缺点费内存、可能不一致。
  • 方案 2：布隆过滤器——应用层前置拦截，元素肯定不存在则直接返回（不查 Redis/DB）。优点内存占用少、无多余 key；缺点实现复杂、存在误判、不支持删除。

布隆过滤器原理：底层是一个bitmap 位数组（每位 0/1），初始化全 0。一个 key 来后经 3 次 hash 计算，模数组长度得到下标，把对应位置 0→1；查询同理（三个位置都是 1 则认为可能存在）。可能误判（hash 碰撞），误判率一般 ≤5% 可接受，不至高并发压垮 DB。

2缓存击穿

定义：单个热点 Key（如秒杀商品）过期瞬间，大量并发请求直达数据库，造成数据库单点压力。与雪崩区别：击穿是某一个 key，雪崩是很多 key。

  • 方案 1：互斥锁（分布式锁）——缓存失效时不立即 load db，先用 setnx 设互斥锁，拿到锁才 load db 并回填缓存，否则重试 get。优点强一致；缺点性能差、可能死锁。
  • 方案 2：逻辑过期——存 key 时把过期时间字段一起存进缓存，不给 key 设真实过期；查询时判断是否过期，过期则另开线程同步数据、当前线程先返回旧数据。优点高可用、性能优；缺点不能保证绝对一致、数据可能不是最新。
3缓存雪崩

定义：大量 Key 同一时间段过期（设置缓存时用了相同过期时间）或 Redis 服务宕机，导致大量请求到达数据库、引发雪崩。（与击穿区别：雪崩是很多 key，击穿是某一个 key）

  • 方案 1：给不同 Key 的 TTL 添加随机值（如 10±2 秒），把失效时间分散开。
  • 方案 2：Redis 集群部署（哨兵/集群）提高可用性，避免单节点故障。
  • 方案 3：多级缓存（本地缓存 Caffeine + Redis，降低 Redis 依赖）；降级限流（Nginx / Spring Cloud Gateway，作为保底策略）。
  • 补充：数据库限流 / 熔断（如 Hystrix/Sentinel）保护数据库。
4三兄弟对比 + 口诀
问题定义产生原因解决方案
穿透查不存在的数恶意攻击、数据不存在缓存空值 / 布隆过滤器拦截
击穿热点 key 过期高并发 + 热点 key热点 key 永不过期（逻辑过期）/ 分布式锁互斥重建
雪崩大量 key 同时过期批量相同过期时间、Redis 宕机过期随机值 / 多级缓存 / 熔断降级 / 集群高可用

三兄弟口诀：「穿透无中生有 key，布隆过滤 null 隔离；击穿过期 key，锁与非期解难题；雪崩大量过期 key，过期时间要随机；面试必考三兄弟，可用限流来保底」。

5双写一致性（Redis 与 MySQL）

问题：数据同时存在 Redis 和 MySQL，当数据变化时就出现一致性问题。方案（先声明业务背景：一致性要求高 / 允许延迟一致）：

  • 办法 1：先更 MySQL 再更 Redis——最基础，中小公司首选；简单易用，但改完 DB 后 Redis 改失败会短暂不一致（靠后续失效自动同步）。
  • 办法 2：Redis 延迟双删——先删 Redis 缓存再改 MySQL，延迟 2 秒再删一次；避免旧数据回写，但延迟时间难定、仍有极短不一致。
  • 办法 3：基于 MQ 异步通知——改完 MySQL 发消息到 MQ，消费者更新 Redis；解耦、有重试兜底，适合中大型。
  • 办法 4：基于 Canal 监听 MySQL Binlog——Canal 伪装成 MySQL 从节点读 binlog 自动更新缓存；无侵入、实时性高、一致性最好，适合高并发（电商/直播）。

注意：强一致性场景不建议用缓存，直接查库；最终一致性只适用于接受短期不一致（商品详情、用户信息）。

6分布式锁

实现：主要利用 Redis setnx（SET if not exists）命令实现。获取锁：SET lock value NX EX 10；释放锁：DEL key。使用场景：集群下的定时任务、抢单、幂等性。

  • Redisson：基于 setnx + Lua 脚本（保证原子性）。可重入（hash 存线程标识和重入次数）；看门狗 WatchDog（默认每 10 秒续期一次，业务没执行完就续加锁时间）；锁重试等待（客户 2 不自旋拒绝，会自旋尝试直到拿到锁）。
  • 主从一致性问题：Redisson 锁不能解决主从数据一致（master 宕机切 slave，锁可能丢失）。可以用 Redlock 红锁解决但性能差；非要强一致建议用 Zookeeper 分布式锁。
◆ 费曼

缓存三兄弟说人话：穿透＝查根本不存在的数据（黑客批量打不存在的 ID，Redis 没命中全打 MySQL）→ 缓存空值或布隆过滤器挡在前面；击穿＝一个热点 key 刚好过期，千万人冲（秒杀商品）→ 分布式锁或逻辑过期（先返回旧数据再异步更新）；雪崩＝一大批 key 同时过期（都设了 0 点过期）或 Redis 挂了 → 过期时间加随机值、多级缓存、限流保底。记住一句话：穿透"无中生有"，击穿"独木难支"，雪崩"全军覆没"。

▸ 总结

三兄弟：穿透（查不存在数据→空值缓存/布隆过滤器）、击穿（热点 key 过期→互斥锁/逻辑过期）、雪崩（大量 key 过期/宕机→随机过期/多级缓存/限流降级/集群）；双写一致 4 法：先更DB再更Redis、延迟双删、MQ、Canal 读 binlog（强一致用 Redisson 读写锁、允许延迟用异步）；分布式锁 setnx + Lua，Redisson 可重入+看门狗，主从一致用红锁/Zookeeper。
