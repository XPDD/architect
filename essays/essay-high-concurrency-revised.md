# 论高并发系统的架构设计与性能优化

## 摘要

2024年5月，我参与了某公司"智慧产业供应链 SaaS 平台"项目的架构设计与开发，担任系统架构设计师，负责整体架构设计、微服务拆分、并发控制与技术选型。平台覆盖供应链管理、大宗交易、产品溯源、智能货柜四大核心业务，采用 Spring Cloud Alibaba 微服务架构，划分为 19 个独立部署的服务模块，由统一网关对外提供 40 条路由。项目总投入约500万元，历时25个月，于2026年6月正式上线运行。项目初期采用单体应用架构，随着电商大促流量的冲击，单体在独立伸缩、构建部署与稳定性上的瓶颈日益突出。本文结合笔者的实际工作经验，论述了该项目针对高并发场景的架构设计与性能优化实践，包括：缓存与分布式锁保障并发一致性、异步化与弹性伸缩实现削峰填谷、限流降级与可观测保障系统稳定三个方面。

## 一、项目背景与主要工作

随着县域产业数字化的深入推进，越来越多的传统商贸企业向线上化、平台化转型。某公司决定建设一套覆盖"供、销、溯、柜"全链路的产业供应链 SaaS 平台：既支持供应商、采购商线上撮合与大宗交易，又要为本地农产品提供扫码溯源，还要通过智能货柜触达末端零售。平台注册用户约 30 万、日均订单约 3 万单，日常 QPS 约 200，大促开场 5 分钟内峰值冲到 2000，是日常的 10 倍，对系统的并发处理能力与稳定性提出了很高要求。

我在项目中担任系统架构设计师，负责整体架构设计与技术选型，主持了微服务拆分方案、服务契约（API）设计、网关与注册中心选型，以及 Redis、Redisson、XXL-Job、消息队列等中间件的选型与落地，重点主导了高并发场景下缓存、异步化、限流与可观测体系的建设。项目组共10人，项目于2024年5月正式启动，历时25个月，于2026年6月正式上线运行。

在项目早期，系统以单体应用架构运行。随着业务规模扩大，三个问题日益突出：第一，构建与部署耦合，供应链、大宗交易、溯源、货柜、商城等模块共用一个应用，任一模块改动都触发整体重建与全量回归，多团队并行开发频繁冲突；第二，弹性与可用性相互拖累，电商交易存在明显的大促流量峰值，单体应用无法按模块独立伸缩，高并发的交易模块与低频的后台模块共命运，个别模块的故障可能拖垮整个平台；第三，大促高峰期数据库 QPS 由日常的 800 骤增至 6500，热点商品查询与库存扣减集中在同一张表，接口 P95 延迟一度超过 2 秒。

## 二、高并发系统的核心设计原则与关键技术

面向高并发，我们的设计主线有三条。先把服务做成无状态，才能按流量水平扩缩；再把高频读和耗时写分别交给缓存与消息队列，把洪峰在时间上摊平；最后用限流、降级和可观测兜住底线，超限即拒绝、故障即隔离，并用指标验证每一次优化的实际效果。

关键技术手段包括：弹性伸缩（按模块水平扩缩实例，如对交易模块配置自动扩缩容）、多级缓存（本地缓存 + Redis 分布式缓存）、异步化（消息队列解耦 + 分布式任务调度）、限流（令牌桶 / 计数器）、熔断降级、分布式锁（保证并发写的一致性）等。这些手段协同实现目标：缓存挡"读洪峰"、异步挡"写洪峰"、限流挡"超容洪峰"、弹性伸缩挡"规模增长"——共同把瞬时流量"削平、拦下、分散"，既保证高吞吐，又把端到端延迟控制在可接受范围。

## 三、高并发架构方案的落地实践

下面结合我在项目中的实践，从"并发一致性、削峰填谷、保护与可观测"三个方面，说明高并发方案的选型依据、落地过程中的关键挑战及应对措施。

## （一）缓存与分布式锁：保障并发一致性

大促期间热点商品查询与库存扣减是两大并发热点。选型上，我们对比了"数据库乐观锁"与"分布式锁"：对库存这类高频热点数据，乐观锁冲突频繁、重试开销高，最终采用 Redis + Redisson 分布式锁保证强一致，避免超卖；在缓存策略上，将热点商品、首页聚合数据等缓存至 Redis，并对关键缓存设置合理的过期与失效策略，减少缓存穿透与雪崩。

落地中的关键挑战是"缓存与数据库的一致性"以及"并发扣减的原子性"。应对措施：库存扣减、货柜订单同步等临界操作通过 Redisson 分布式锁串行化，配合 Lua 脚本保证"查库存—扣减—回写"的原子性；热点缓存采用"先更新数据库、再删除缓存"的策略，并在失效瞬间用分布式锁做"单飞"重建，避免击穿。改造前大促高峰库存扣减接口 P99 达 1.2 秒并出现过 3 笔超卖，引入 Redisson 分布式锁与 Lua 原子脚本后，P99 降到 300ms 以内，未再发生超卖。

## （二）异步化与弹性伸缩：削峰填谷

大促尖峰流量无法通过单纯扩容承接，必须在时间维度上削峰、在空间维度上分摊。选型上，我们引入分布式任务调度平台 XXL-Job，编排货柜订单/设备/库存同步、采购需求过期处理、访问日志清理等 44 个定时任务，把周期性批量任务从请求链路中剥离；同时基于消息队列抽象层（支持 local/redis/rocketmq/kafka/rabbitmq 多通道），将 IoT 设备消息总线、WebSocket 消息广播等场景异步化，避免高并发时同步阻塞拖垮服务。

针对单体无法按模块独立伸缩的问题，我们通过微服务拆分使交易、溯源等热点模块可以独立水平扩展：为高并发模块配置多实例 + 网关负载均衡，大促前通过压测确定容量并提前扩容，大促后回收实例，实现弹性伸缩。上线首周出现过一次货柜库存重复入账，原因是 MQ 重投后消费端未做幂等。我们随后以设备号加业务流水号作为唯一键去重，并在 XXL-Job 侧配置 3 次失败重试与告警，此后未再复现。实践表明，大促峰值流量被平滑削峰，货柜设备数据按时同步，系统未因瞬时流量出现阻塞。

## （三）限流、降级与可观测：保护系统稳定

高并发场景下，系统必须"知道自己什么时候会被冲垮"，并提前保护。针对溯源码 C 端公开查询接口（无需登录、面向消费者），我们基于 Redis 计数器实现限流：同一 IP 每分钟最多 10 次、同一溯源码每分钟最多 5 次，超限返回 HTTP 429，防止公开接口被恶意刷量。在限流位置上，网关限流配置集中、生效快，但改一次规则要走发布流程，粒度也只能到路由级；应用层限流可以按 IP、溯源码等业务维度灵活调整，因此选择在应用层基于 Redis 计数器实现。同时，对非核心链路配置降级策略，在压力或故障时返回兜底数据，保证核心交易链路可用。

在可观测层面，此前大促出现问题只能逐个容器翻日志，定位一次慢接口平均要 40 分钟。我们接入 Prometheus 统一采集 JVM、接口性能与慢 SQL 指标，并生成全链路 traceId；在此基础上，进一步将 Prometheus 指标与日志查询能力通过 MCP（Model Context Protocol）标准协议开放给智能分析 Agent，慢接口出现时 Agent 可自动拉取指标、比对基线、沿 traceId 下钻到具体服务与 SQL，直接输出根因定位与修复建议。定位方式从"逐容器翻日志"转变为"指标发现、Agent 定位"，平均定位时间缩短到 5 分钟以内。实践表明，公开查询接口未出现被刷量拖垮服务的情况，系统整体可用性保持在 99.9% 以上。

## 四、实施效果与总结

经过近25个月的建设，智慧产业供应链 SaaS 平台于2026年6月顺利交付上线。平台共运行 19 个服务模块，网关配置 40 条路由，注册用户约 30 万，日均订单约 3 万单，大促峰值 QPS 达到 2000，接口 TP99 稳定在 300ms 以内，系统可用性保持在 99.9% 以上；产品溯源累计生成溯源码超过 500 万个，智能货柜接入设备 300 余台。得益于缓存、异步化、限流与弹性伸缩的组合运用，平台在多次大促活动中平稳承接了流量洪峰，客户反馈良好。

回顾整个项目，我最大的体会是：高并发不是靠某一种"神器"，而是"缓存挡读、异步挡写、限流挡洪峰、伸缩挡规模"的组合工程；且性能优化必须以可观测数据为依据，先量化瓶颈、再针对性设计，才能避免盲目堆机器。本项目中仍存在一些不足：一是容错治理尚未引入统一熔断组件，计划 2026 年第三季度完成选型并在非核心链路灰度；二是跨服务事务仍以补偿重试为主，计划引入 Seata TCC 处理订单与库存的强一致场景；三是多集群容灾仍在完善，2026 年底前完成双活演练。我将不断学习，提升自身架构设计能力，为企业数字化转型贡献自己的力量。
