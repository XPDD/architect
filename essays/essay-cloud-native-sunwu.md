# 论云原生架构及其应用

> 项目素材：sunwu-claw（数字员工运营管理平台）
> 时间线：2024-11 启动 → 2026-06 交付试运行，历时 20 个月，投入约 400 万元
> 主线：从单体集中式 → 云原生架构的演化过程与决策（CBSD 构件化集成，非自研拆分；服务网格见第二篇）
> 状态：数据已按真实口径填写（200 Agent / 50 QPS / 2天发布）

## 摘要

2024年11月，我参与了某公司"数字员工运营管理平台"项目的架构设计与开发，担任系统架构设计师，负责整体架构设计与技术选型。该系统以多智能体（Agent）的注册、部署、记忆同步、能力装配与协作治理为核心，采用了构件化软件开发（CBSD）方法，直接集成 OpenClaw 运行时、ClawHub 技能市场、飞书渠道桥接等开源构件，平台自身聚焦于 Agent 实例管理、Skill 管理与记忆管理等编排能力。项目总投入约400万元，历时20个月，于2026年6月与合作单位共同交付试运行，获得客户一致好评。项目启动初期采用单体集中式架构，随着 MCP 工具治理、Skill 能力装配、Agent 生命周期管理等模块的持续演进，部署单元增长至 7 个，环境变量增至 78 项，集成复杂度急剧上升。本文结合笔者的实际工作经验，论述了该项目基于 CBSD 集成、从单体架构向云原生架构演化的过程，包括：容器化改造与构件标准化交付、Kubernetes 编排与 Agent 状态外置、可观测性与 GitOps 自动化交付三个方面。

## 背景

随着人工智能技术的快速普及，越来越多的企业开始部署大量 AI 智能体（Agent）处理日常业务，但随之而来的却是沉重的运维负担：中心记忆仓库更新需要人工 SSH 登录每台机器逐个执行；新建 Agent 需要手工注册账号、配置邮箱、编排工作流，耗时数小时；Agent 状态、Token 消耗、任务进度均不可视。为从根本上解决上述问题，该公司决定投资建设一套统一的数字员工运营管理平台。我所在的公司承担该项目，我被任命为系统架构设计师，负责整体架构设计与中间件选型。项目组共20人，项目于2024年11月正式启动，历时20个月，于2026年6月与合作单位共同交付试运行。系统核心功能包括 Agent 生命周期管理、MCP 工具治理、Skill 能力装配、记忆同步与协作治理。

## 一、项目的总体结构与个人职责

本平台以 Agent 生命周期管理为主线，覆盖"注册→部署→能力装配→记忆同步→协作治理"全生命周期。架构上采用构件化软件开发（CBSD）方法，直接集成 OpenClaw（Agent 运行时）、ClawHub（Skill 市场）、飞书渠道桥接等开源构件，并在此基础上构建管理编排层，主要功能模块包括：Agent 实例管理——维护每台实例的部署位置与运行状态（在线/离线/工作中）；Skill 能力装配——实现技能的搜索、安装、分发与版本管理；记忆管理——基于 Git 仓库实现组织/项目/角色/Agent 四层记忆分发；LLM 统一接入网关——承担多模型路由与计费；以及会话数据分析引擎。平台自身以 Next.js 16 为核心应用，LLM 网关基于 NestJS 11，数据分析引擎基于 Python + Prefect，Gateway 服务以 Go 实现 MCP 协议的工具接入。

我作为系统架构设计师，主持了 CBSD 构件选型与集成方案、容器化方案、Kubernetes 资源设计、网络策略与 CI/CD 流水线的架构设计工作，并主导了相关中间件（Prefect、Nexus 镜像仓库等）的选型与落地。

## 二、架构演化的动因分析

在项目早期，系统以单体集中式架构运行：所有平台逻辑集中在一个 Next.js 应用中，Agent 通过 SSH 远程管理，配置依赖机器上的环境变量与启动参数。随着业务快速演进，以下问题日益突出：

第一，**CBSD 集成规模扩大，集成难度上升**。平台集成的构件（OpenClaw 运行时、ClawHub、飞书桥接、LLM 网关、Prefect 分析引擎、Hermes 等）不断增多，构件间通过环境变量、端口、协议相互依赖，任何构件的升级或配置变更都面临连锁影响，集成回归成本高。

第二，**配置与依赖爆炸**。环境变量数量增长至 78 项，各构件对运行环境的要求（Node 版本、Python 版本、系统库、K8s 权限）各不相同，主机级部署难以统一，构建与部署依赖人工操作，极易因环境差异导致"在我机器上能跑"的问题。

第三，**治理逻辑与业务逻辑耦合**。MCP 工具的风险路由、提示注入防护、Agent 状态监控等横切关注点散落在平台代码中，难以独立演进与复用。

基于上述动因，我们决定向云原生架构演化，将"基础设施的关注点"（部署、编排、网络、配置、可观测性）从平台代码中剥离，交由平台层统一管理，使 CBSD 集成出的能力能够以标准化的方式交付与运维。

由此确立本文的总论点：**云原生架构的本质，是通过把基础设施关注点从业务代码中最大化剥离，使数字员工平台的运行状态外置化、交付声明化、运维自动化、运行可观测化**。下面围绕这一总论点，从容器化与构件标准化交付、Kubernetes 编排与 Agent 状态外置、可观测性与自动化交付三个分论点展开论述。

## 三、云原生架构的演化实践

在方案设计阶段，我们以云原生架构的原则与模式为指引，确保改造方向符合其核心理念。云原生架构的本质，是把云应用中的"非业务代码"（处理弹性、韧性、安全、可观测性、灰度等非功能特性的代码）最大化剥离，交由云设施接管，使业务代码与三方构件只关注自身逻辑。其设计原则包括：服务化、弹性、可观测、韧性、所有过程自动化、零信任、架构持续演进；主要架构模式包括：服务化、Mesh 化、Serverless、存储计算分离、分布式事务、可观测、事件驱动。同时，微服务设计需遵循四类约束——个体约束（单一职责、低耦合）、横向关系（可发现性、可交互性）、纵向约束（数据存储隔离，数据是服务的私有资产）、全局分布式约束（故障发现时效性与根因精确性）。本项目正是围绕这些原则与模式逐项落地的。

### 分论点一：容器化改造与构件标准化交付（解决"环境依赖、集成难维护"）

构件化集成面临的核心问题是异构运行环境与版本漂移，容器化通过镜像封装每个构件的完整运行环境，实现"一次构建、到处运行"，是云原生演化的第一步。

我们将平台自身与所集成的构件分别容器化：平台主体采用多阶段 Dockerfile 构建，以 node:22-alpine 为基础镜像，将依赖安装、构建、运行分离，最终产物仅包含运行时与 `.next/standalone` 输出；数据分析引擎基于 prefecthq/prefect:3.7.7-python3.11 镜像构建；Gateway 服务采用 Go 编译为单一二进制。每个构件独立成镜像，版本与运行环境完全封装，消除"环境差异"问题。

在是否容器化的决策上，我们权衡了容器化的资源开销与消除环境漂移的价值。鉴于构件异构性高、版本迭代频繁，最终选择全量容器化。实践表明，新环境从"配置数小时"缩短为"拉镜像即运行"，构件升级由整体重建改为替换镜像 Tag 即可完成，集成回归范围从"全量回归"收敛为"仅验证所涉构件"。

### 分论点二：Kubernetes 编排、Agent 状态外置与零信任安全（解决"资源调度、状态管理与安全边界"）

Kubernetes 提供统一的调度、编排与自愈能力，同时以 StatefulSet 与状态机管理有状态实例；网络策略实现服务间的最小化访问。对于数字员工平台，Agent 实例天然是有状态的（在线状态、记忆、会话、沙箱），其状态管理正是云原生能力的关键应用场景。

在编排与状态层面，我们引入 Kubernetes 集群，为核心服务定义 Deployment，配置就绪与存活双探针（/health），实现滚动更新与故障自愈，并配置资源请求与限额保障服务质量，对高并发的 LLM 网关配置 HPA（以 CPU 70% 为阈值，1 至 5 副本自动伸缩），体现**韧性**与**弹性**原则。针对 Agent 实例的有状态特性，采用 StatefulSet 管理实例生命周期，通过状态机（部署中/在线/离线/工作中等状态）与心跳机制实现实例状态的统一登记与监控；Agent 状态、记忆、会话、沙箱等资产通过 PostgreSQL 与阿里云 OSS 持久化，实现"状态外置"，实例重建后状态可恢复，体现**存储计算分离**模式，也落实微服务**纵向约束**中的"数据存储隔离"。

在安全层面，针对 LLM 网关设计 NetworkPolicy 实施零信任：入口仅允许核心平台与 Agent 集群访问其 3001 端口，出口仅放行 DNS、PostgreSQL（5432）与外部 LLM 提供商的 HTTPS（443），体现**零信任**原则；同时利用 Kubernetes client-node 实现 WebShell 与 WebSocket 双向代理，提供对远端 Agent 实例与沙箱的安全运维通道。

相比 Docker Compose 的单机编排，Kubernetes 提供了细粒度资源配额、自动伸缩、有状态实例管理与网络策略能力，代价是运维复杂度上升。我们通过统一的基础设施即代码（Terraform）管理与规范化清单，将复杂度收敛于平台层。实践表明，高峰期服务自动扩容、低谷期自动回收，Agent 实例状态可迁移、可恢复；网络策略将服务暴露面收敛为 3001/5432/443 三个必要端口，攻击面可穷举、可审计。

### 分论点三：可观测性、工作流编排与 GitOps 自动化交付（解决"可观测与部署自动化"）

云原生架构强调可观测、所有过程自动化与持续交付：只有让系统运行状态可度量、任务执行可编排、部署变更可声明式管控，才能实现"无人值守"的稳定运营。

在可观测性层面，我们构建了 Logging（结构化业务日志）、Metrics（服务指标与资源度量）、Tracing（会话与任务全链路追踪）三支柱，实现系统的多维度可观测，监控告警通过飞书渠道桥接（Webhook）自动触达相关人员，运维无需值守即可获知异常。在任务治理层面，会话数据分析涉及大量长时任务，若使用裸 CronJob 难以管理依赖与失败重试，我引入 Prefect 作为工作流引擎，通过 Kubernetes work pool 将每个 Flow 提交为独立的 K8s Job 执行，支持 DAG 依赖、失败重试、并发限流与幂等控制，将每日的数据分析、胜任力快照等任务统一编排为夜间流水线，体现了**事件驱动**与**所有过程自动化**原则。在交付层面，采用 GitOps 模式：GitHub Actions 按代码变更自动判定需重建的服务镜像并推送至私有 Nexus 仓库，再由流水线修改独立部署仓库中的镜像 Tag 并推送，实现环境隔离（staging/prod）与变更可审计，实现了面向终态的声明式交付。

相比自建调度器，Prefect 提供成熟的 DAG 与重试机制，降低开发成本；相比直接更新集群，GitOps 保证部署变更可回滚、可审计。实践表明，三支柱可观测使会话与任务链路可追踪、故障可快速定位；数据分析任务按计划稳定执行；部署过程全自动、可追溯，平均每 2 天即可发布一个新版本，异常实例在秒级被自动摘除并重启。值得注意的是，架构本身也遵循"持续演进"原则——当前以 Kubernetes 编排承载服务，后续将结合服务规模增长，逐步引入 Serverless 处理突发性轻量任务，并评估服务网格（Mesh 化）将连接、安全、流量控制等能力进一步下沉至基础设施层，使架构具备面向未来的演进能力。

## 结尾

经过近20个月的项目开发，数字员工运营管理平台于2026年6月与合作单位共同交付试运行。目前平台管理 Agent 数量超过200个，日均处理任务1000余项，LLM 网关峰值并发达到50 QPS，系统可用性保持在 99.9% 以上，客户反馈良好。在发布交付层面，得益于 GitOps 流水线，平台实现平均每2天发布一个新版本，发布过程全自动、可回滚，早期人工 SSH 逐机部署的发布流程被彻底自动化；配合就绪与存活双探针，发布过程中异常实例可在秒级被自动摘除并重启，故障恢复不再依赖人工介入。云原生架构的落地，使系统具备了快速交付、弹性伸缩与高可用的能力，为公司节省了大量运维人力。回顾整个项目，我最大的体会是：数字员工平台治理的难点集中于 **Agent 的状态管理**——Agent 天然是有状态、长生命周期的实体，其在线状态、记忆、会话与沙箱资产分散在多台实例上，只有通过状态外置化、统一登记与可恢复设计，才能真正做到可管、可控、可迁移；这也是本项目云原生改造价值最集中的落点。当然，本项目中仍存在一些不足，例如多集群容灾尚未完全实现，跨集群的备份恢复与容灾切换方案仍在完善中，后续我们将结合服务规模增长逐步完善。我将不断学习，提升自身架构设计能力，为企业数字化转型贡献自己的力量。
