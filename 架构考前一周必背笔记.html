数据库系统 · 数据库设计六阶段

  1. 需求分析：分析数据存储要求，产出数据流图、数据字典、需求说明书；获得用户三个要求——信息要求、处理要求、系统要求。
  2. 概念结构设计：设计 E-R 图（实体-联系图）。步骤：选择局部应用 → 逐一设计分 E-R 图 → E-R 图合并。合并时 3 类冲突：
    • 属性冲突：同一属性可能存在于不同分 E-R 图中。
    • 命名冲突：相同意义的属性命名不同，或同名属性意义不同。
    • 结构冲突：同一实体在不同分 E-R 图属性不同；同一对象在一图是实体、另一图是属性。
  3. 逻辑结构设计：E-R 图 → 关系模式。步骤：确定数据模型 → 转换 → 确定完整性约束 → 确定用户视图。
  4. 物理设计：确定数据分布、存储结构和访问方式。
  5. 数据库实施阶段：建库、编制与调试程序、组织数据入库、试运行。
  6. 运行和维护阶段：投入运行后不断评价、调整与修改。

软件架构风格

#架构风格常考关键字及实例简介
1数据流-批处理传统编译器，每个阶段产生的结果作为下一阶段输入，区别在于整体一个接一个，以整体为单位
2数据流-管道-过滤器（同上）一个接一个，前一个输出是后一个输入
3调用/返回-主程序/子程序无显示调用，主程序直接调用子程序
4调用/返回-面向对象无对象是构件，通过对象调用封装的方法和属性
5调用/返回-层次结构无分层，每层最多影响其上下两层，有调用关系
6独立构件-进程通信无进程间独立的消息传递，同步异步
7独立构件-事件驱动（隐式调用）事件触发推动动作，如语法高亮、语法错误提示不直接调用，通过事件驱动
8虚拟机-解释器自定义流程，按流程执行，规则随时改变，灵活定义、业务灵活组合。机器人解释自定义规则，解释引擎、存储区、数据结构
9虚拟机-规则系统（同上）规则集、规则解释器、选择器和工作内存，用于 DSS、AI、专家系统
10仓库-数据库现代编译器 IDE，以数据为中心，又称数据共享风格中央共享数据源，独立处理单元
11仓库-超文本（同上）网状链接，多用于互联网
12仓库-黑板（同上）语音识别、知识推理等复杂问题，黑板、知识源、控制
13闭环过程控制汽车巡航定速、空调温度调节，设定参数并不断调整发出控制命令并接受反馈，循环往复达到平衡
14C2 风格构件和连接件、顶部和底部通过连接件绑定、按一组规则运作的并行构件网络

分类归纳

  • 数据流风格：批处理、管道-过滤器（实例：传统编译器）
  • 调用/返回风格：主程序/子程序、面向对象、层次结构
  • 独立构件风格：进程通信、事件驱动（隐式调用）（实例：语法高亮、错误提示）
  • 虚拟机风格：解释器、规则系统（应用：DSS、AI、专家系统）
  • 仓库风格（数据共享）：数据库、超文本、黑板（实例：IDE）
  • 过程控制风格：闭环过程控制（实例：巡航定速、空调温控）
  • C2 风格：构件和连接件、顶部和底部，并行构件网络

基于架构的软件开发（ABSD）

ABSD 是架构驱动，强调由业务、质量和功能需求的组合驱动架构设计；采用视角和视图描述软件架构，采用用例和质量属性场景描述需求——用例描述功能需求，质量属性场景描述质量需求（非功能需求）。

使用 ABSD，设计活动可从项目总体功能框架明确就开始，即需求获取和分析还没完成就开始了软件设计。

三个基础：

  1. 功能的分解：使用已有的基于模块的内聚和耦合技术；
  2. 选择架构风格：通过选择架构风格实现质量和业务需求；
  3. 软件模板的使用：软件模板利用了一些软件系统的结构进行复用。

ABSD 是递归的，且迭代的每个步骤都清晰定义；不管设计是否完成，架构总是清晰的，有助于降低架构设计的随意性。

六步过程：

体系结构需求 → 体系结构设计 → 体系结构文档化 → 体系结构复审 → 体系结构实现 → 体系结构演化

各步骤之间可迭代、可回退（图中虚线箭头标注 0:N、0:M），例如复审不通过则返回架构设计阶段重新设计、文档化，再复审。

步骤内容
1. 架构需求重在掌握标识构件的三步：① 生成类图 → ② 对类进行分组 → ③ 把类打包成构件。整体流程：需求获取（来自需求库）→【标识构件】→ 需求评审
2. 架构设计将需求阶段的标识构件映射成构件并分析。流程：提出架构模型 → 映射构件 → 分析构件相互作用 → 产生架构 → 设计评审
3. 架构文档化产出两种文档：架构（体系结构）规格说明、测试架构（体系结构）需求的质量设计说明书。文档至关重要，是所有人通信的手段，关系开发成败
4. 架构复审由外部人员（用户代表、领域专家）参加，复审架构是否满足需求、质量问题、构件划分合理性；复审不过则返回架构设计阶段
5. 架构实现用实体显示架构：实现构件，构件组装成系统
6. 架构演化对架构进行改变，按需求增删构件，使架构可复用

软件系统的质量属性

开发期质量属性（开发者关注，6 个）

  • 易理解性：设计被开发人员理解的难易程度。
  • 可扩展性：因适应新需求或需求变化而增加新功能的能力，也称灵活性。
  • 可重用性：重用软件系统或某一部分的难易程度。
  • 可测试性：对软件测试以证明其满足需求规范的难易程度。
  • 可维护性：修改缺陷、增加功能、提高质量属性时，识别修改点并实施修改的难易程度。
  • 可移植性：从一个运行环境转移到另一个不同运行环境的难易程度。

运行期质量属性（用户关注，7 个）

  • 性能：及时提供相应服务的能力，如速度、吞吐量、容量。
  • 安全性：兼顾向合法用户提供服务与阻止非授权使用的能力。
  • 可伸缩性：用户数和数据量增加时维持高服务质量的能力。
  • 互操作性：与其他系统交换数据和相互调用服务的难易程度。
  • 可靠性：一定时间内持续无故障运行的能力。
  • 可用性：一定时间内正常工作时间所占比例，受错误、攻击、高负载影响。
  • 鲁棒性：非正常情况（非法操作、软硬件故障）下仍能正常运行的能力，也称健壮性或容错性。

质量属性场景描述

质量属性场景是描述系统如何满足特定质量属性需求的情境，由 6 部分组成：

  • 刺激源（谁）：生成该刺激的实体（人、计算机系统或任何其他刺激器）。
  • 刺激（做什么）：当刺激到达系统时需要考虑的条件。
  • 环境（在什么环境下）：该刺激在某些条件内发生，系统可能处于过载、运行或其他情况。
  • 制品（对哪个功能）：某个被激励的制品，可能是整个系统或系统的一部分。
  • 响应（得到什么反馈）：刺激到达后所采取的行动。
  • 响应度量（对反馈进行度量）：响应发生时应当能以某种方式度量，以对需求进行测试。
口诀：谁 · 干什么 · 什么环境 · 对啥 · 啥反馈 · 怎么量
