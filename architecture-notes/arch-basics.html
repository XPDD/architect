▸ 核心要点
1SOA — 面向服务的架构风格

核心思想

粗粒度、松耦合的服务架构。将分散的系统功能包装成"服务窗口"，通过统一的 ESB（企业服务总线）对外提供标准化服务。类比：政务服务中心——市民（应用）不需要知道找哪个部门，只需在窗口提交申请。

实现技术

  • Web Service：基于 HTTP/HTTPS、XML/JSON 实现跨平台通信
  • 服务注册表：服务的发现与查找
  • ESB（企业服务总线）：消息路由、转换、协议适配的中间件
1.1WebService 三大核心组件 + 关键技术
A
服务提供者 Provider
  • 提供具体服务，发布服务到注册中心
  • 处理服务请求并返回响应
B
服务请求者 Consumer
  • 使用服务的实体
  • 通过网络请求访问服务
C
服务注册中心 Registry
  • 管理服务注册与查找
  • 类似黄页电话簿
口诀
WSDL · SOAP · UDDI
  • WSDL = 服务说明书（办事指南）
  • SOAP = 信封格式（统一格式）
  • UDDI = 黄页电话簿（服务登记）

WebService 工作流程

服务注册（发布 WSDL）→ 服务查找（查询注册中心获取 WSDL）→ 服务调用（构造 SOAP/HTTP 请求）→ 服务响应（返回结果）

2DSSA — 特定领域软件架构

定义与特征

专用于某类特定任务的软件架构集合，特征：领域性、普遍性、抽象性、可复用性。例如：医疗电子病历系统属于垂直域；收费系统（购物/教育共用）属于水平域。

1
领域分析
  • 目标：获得领域模型（领域需求）
  • 识别信息源：现存系统、技术文献、专家、市场分析等
  • 产出：领域模型
2
领域设计
  • 目标：获得DSSA（高层次设计）
  • 不是单个系统，是适应领域多系统需求的通用架构
  • 产出：DSSA 架构
3
领域实现
  • 目标：开发可重用信息/构件
  • 从现有系统提取或新开发
  • 产出：可复用的构件
角色
四种参与角色
  • 领域专家：提供领域知识
  • 领域分析人员：控制分析过程
  • 领域设计人员：开发 DSSA
  • 领域实现人员：开发构件
3ABSD — 基于架构的软件开发

核心特点

  • 架构驱动：由业务、质量、功能需求的组合驱动架构设计
  • 采用视角和视图描述架构，用例描述功能需求，质量属性场景描述非功能需求
  • 设计可在需求分析未完成时就启动，递归且迭代
1
功能分解
  • 使用基于模块的内聚和耦合技术
2
架构风格
  • 选择架构风格实现质量与业务需求
3
软件模板
  • 利用已有系统的结构进行复用
流程
六大步骤
  • 架构需求 → 设计 → 文档化
  • → 复审 → 实现 → 演化
4CBSD vs ABSD 对比
维度CBSD（基于构件）ABSD（基于架构）
核心目标通过预制构件快速组装系统通过架构设计保障质量与扩展性
关注焦点构件的复用性与集成方式系统整体结构与关键质量属性
典型场景企业级应用快速开发（ERP/CRM）复杂系统（自动驾驶/分布式交易平台）
复用单元业务级构件（支付模块、用户管理组件）架构模式（微服务、分层架构）
变更影响构件替换可能导致接口冲突架构变更需重新评估质量属性
◆ 费曼

SOA、DSSA、ABSD 到底在说什么？ SOA 就像政府服务中心——把各个部门的业务包装成统一窗口对外，老百姓不用管后面是谁在干活。DSSA 就像是建医院的"标准图纸"——不同医院需求不同，但图纸（架构）是通用的，改改就行。ABSD 则是"先画骨架再填肉"——做复杂系统时先把大的结构定好，而不是一边写代码一边想结构。三个东西层层递进：SOA 告诉你"怎么拆"、DSSA 告诉你"怎么复用"、ABSD 告诉你"怎么建"。

▸ 总结

SOA 以松耦合服务 + ESB解决集成问题，DSSA 通过领域分析→设计→实现产出可复用架构，ABSD 以架构驱动、先骨后肉的方式递归迭代构建系统——三者共同构成架构设计的基础理论体系。
