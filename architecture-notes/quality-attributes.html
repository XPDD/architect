▸ 核心要点
1开发期 vs 运行期质量属性
开发期（6个）— 开发者关注
  • 易理解性：设计被开发人员理解的难易
  • 可扩展性：适应新需求增加功能的能力（灵活性）
  • 可重用性：重用系统或其部分的难易
  • 可测试性：测试满足需求规范的难易
  • 可维护性：识别修改点并实施修改的难易
  • 可移植性：迁移运行环境的难易
vs
运行期（7个）— 用户关注
  • 性能：及时响应能力（速度、吞吐量、容量）
  • 安全性：阻止非授权使用的能力
  • 可伸缩性：用户/数据增加时维持服务质量
  • 互操作性：与其他系统交换数据的能力
  • 可靠性：持续无故障运行的能力
  • 可用性：正常工作时间所占比例
  • 鲁棒性：非正常情况下仍能运行（容错性）

真题考点：2026上-Q2

全部属于运行期质量属性的是：安全性、可用性、性能（可修改性、可测试性、可移植性、可维护性、可扩展性均为开发期）

2可靠性 vs 可用性 — 易混淆对比
R
可靠性 Reliability
  • 强调不故障（少出错）
  • 指标：MTTF / MTBF / MTTR
  • 设计策略：心跳、Ping/Echo、冗余、选举
  • 例：Provider A 全年零故障 → 高可靠性
A
可用性 Availability
  • 强调故障后快速恢复
  • 指标：可操作时间比例
  • 设计策略：心跳、Ping/Echo、冗余、选举
  • 例：Provider B 停机5小时但快速恢复 → 高可用性

核心区别：可靠性 = 不出事；可用性 = 出事了能快速修好。

3架构评估 9 大质量属性 + 设计策略
属性核心定义关键设计策略
性能响应时间、吞吐量优先级队列、增加资源、并发机制、资源调度、缓存、负载均衡
可靠性正常运行不故障（MTTF/MTBF量化）心跳、Ping/Echo、冗余、选举；容错（自动修复）、健壮性（安全终止）
可用性可操作时间比例，强调恢复速度心跳检测、冗余切换（主从库/灾备）、状态同步（检查点/回滚）
安全性机密性/完整性/不可抵赖性/可控性入侵检测、身份认证（OAuth/JWT）、访问控制（RBAC）、数据加密（TLS/SSL）、审计追踪
可修改性低成本高效变更，含维护/扩展/重组接口-实现分离、抽象、信息隐藏、模块化、松耦合接口、微服务动态配置
功能性完成预期任务，多构件协作接口标准化（OpenAPI）、服务编排（工作流引擎）
可变性架构适应未来变更，支持产品线配置驱动（Feature Toggle）、抽象核心逻辑（领域驱动设计）
互操作性与其他系统交换数据或调用服务协议兼容（REST/gRPC）、数据格式统一（JSON Schema/Protobuf）
易用性用户界面和交互设计，学习曲线用户体验优化、交互流程简化

可修改性场景示例

刺激源：开发人员 → 刺激：修改功能 → 环境：设计时 → 制品：UI层 → 响应：定位修改点、不影响其他功能、测试、部署 → 响应度量：影响元素数量、成本、对其他功能影响程度

性能场景示例（电商高负载购物日）

刺激源：购物用户 → 刺激：浏览商品、加购物车、结算 → 环境：12月24-25日，流量增至10倍 → 制品：网站前后端系统 → 响应：负载均衡、缓存静态内容、垂直/水平扩展 → 响应度量：网页加载时间、服务器资源利用率、错误率

◆ 费曼

质量属性到底在讲什么？ 质量属性就是评价一个软件"好不好"的维度。开发期属性是"好写不好写"（好不好懂、好不好改、好不好测、能不能移植），运行期属性是"好用不好用"（快不快、安不安全、会不会崩、崩了能不能恢复）。可靠性和可用性的区别最好记：可靠性像"从不得病"，可用性像"得病了很快能好"。质量属性场景就是用6个要素把"在什么情况下系统该怎么表现"说清楚——谁、做什么事、在什么条件下、影响哪个部分、系统怎么应对、怎么衡量结果。

▸ 总结

质量属性分开发期6个（开发者视角）和运行期7个（用户视角），架构评估聚焦9大属性各有设计策略；可靠性=不出事，可用性=出事了快恢复；用6要素场景（刺激源→刺激→环境→制品→响应→响应度量）将模糊的质量需求转化为可验证的量化指标。
