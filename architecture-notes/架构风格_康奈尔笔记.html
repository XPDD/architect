1数据流风格
A
批处理序列
  • 固定顺序的计算单元，同步顺序执行
  • 前一步完成后下一步才开始
  • 数据以整体方式传递，必须完整
  • 例：批量图像处理（缩放→加水印→转换格式）
  • 特点：一次性处理大量数据、离线执行
B
管道-过滤器
  • 每个构件（过滤器）读取输入流 → 处理 → 输出流
  • 前一个输出 = 后一个输入，连接件 = 管道
  • 例：编译器、文本处理管道（分词→词干提取→情感分析）
  • 特点：逐步处理、实时/近实时、可组合扩展

核心区别：批处理 = 批量+离线+整体传递；管道过滤器 = 流式+实时+逐步传递。早期编译器用管道-过滤器，凡是要一步一步处理的都可考虑此风格。

2调用/返回风格
1
主程序/子程序
  • 单线程控制，问题划分处理步骤
  • 构件 = 主程序+子程序，连接件 = 过程调用
  • 子程序可合成模块
2
面向对象
  • 对象 = 抽象数据类型实例
  • 连接件 = 对象间函数/过程调用
  • 强调封装、继承、多态
3
层次结构
  • 每层为上层服务、使用下层服务
  • 只能见到邻接层，修改只影响相邻两层
  • 优点：分解复杂问题为增量序列
  • 缺点：调用开销，非所有系统可分层
4
客户端/服务器
  • 构件间显式调用关系
  • C/S 是最典型的调用/返回实现
3独立构件风格
1
进程通信
  • 构件 = 独立进程，连接件 = 消息传递
  • 点对点、异步/同步、远程过程调用
  • 例：多线程文件下载器（下载线程 + 监控线程通信）
2
事件驱动（隐式调用）
  • 不直接调用，而是触发/广播事件
  • 注册事件处理程序，事件触发时自动调用
  • 例：GUI 应用（点击按钮生成事件）
  • 优点：支持复用、方便维护演化
  • 缺点：构件放弃计算控制权，被动响应
4虚拟机风格
A
解释器
  • 四要素：解释引擎 + 被解释代码存储区 + 引擎状态数据结构 + 执行进度记录
  • 缺点：执行效率低
  • 例：Python 解释器，用户输入 "2+3" 返回 "5"
B
基于规则的系统
  • 四要素：规则集 + 规则解释器 + 规则/数据选择器 + 工作内存
  • 领域：AI、DSS（决策支持系统）
  • 例：银行贷款审批（信用评分→审批规则→自动批准/拒绝）
5以数据为中心风格（仓库风格）
仓库风格
  • 数据存储在中央仓库/数据库
  • 各组件读写共享仓库
  • 例：天气预报系统（多数据源 → 中央仓库 → 查询生成预报）
  • 强调：数据集中存储和共享
vs
黑板风格
  • 黑板 = 公共存储区，多个"专家"组件共享
  • 专家根据黑板上信息推断和决策
  • 例：医学诊断系统（放射科+心脏+内科专家 → 黑板 → 综合诊断）
  • 强调：多个专家协作解决非结构化问题
5.1其他特殊风格
∞
闭环控制
  • 软件与硬件 = 反馈循环
  • 输入 → 确定输出 → 环境达到新状态
  • 适合嵌入式系统，连续动作与状态
  • 例：空调逐渐接收室温来调节冷气输出
C2
C2 体系结构风格
  • 通过连接件绑定的并行构件网络
  • 所有构件/连接件都有顶部和底部
  • 构件顶部连连接件底部，构件底部连连接件顶部
  • 构件之间不允许直接连接
7层次架构风格（C/S · B/S · 混合）
架构结构特点优缺点
两层 C/S 客户端(展示+功能) + 服务器(数据) 胖客户端，功能层集成在客户端 开发成本高、难维护升级、安全性差、已不常用
三层 C/S 表示层(客户端) + 功能层(应用服务器) + 数据层(DB) 功能层独立，各层逻辑独立 可并行开发、灵活选平台、安全性好、可扩展性强
三层 B/S 浏览器 + Web服务器 + 数据库 0客户端架构，变种C/S 免客户端开发；安全难控、响应慢（C/S有本地数据）、动态交互弱

选型原则

两层→业务简单/性能敏感/资源有限；三层→安全隔离/业务复用/长期维护的中大型系统（用 gRPC 降通信开销、Docker/K8s 简化部署、Redis 减DB压力）。

混合架构

  • 内外有别：企业内部用 C/S，外部人员访问用 B/S
  • 查改有别：采用 B/S 查询，采用 C/S 修改
  • 注意：混合架构实现困难、成本高
8SOA — 面向服务的架构 + WebService
↔
SOAP
  • 基于 XML 的消息传递协议
  • 企业级、重量级、支持复杂数据类型
  • 配合 WSDL + XML Schema
⚡
REST
  • 基于 HTTP，URL=资源，GET/POST/PUT/DELETE
  • JSON/XML 传输，简洁高效
  • 广泛用于互联网、轻量级应用
📦
ESB
  • 服务间通信中间件，一根管道连接各节点
  • 消息转化、解释、路由
  • 支持同步/异步模式、安全、负载均衡
  • 类比：政务服务大厅的统一窗口
📚
口诀
  • WSDL = 服务说明书
  • SOAP = 信封格式
  • UDDI = 黄页电话簿
  • 组件：提供者 + 消费者 + 注册中心

SOA 应用场景

  • 企业应用集成（EAI）：串起50个老系统办一件事（工商+税务+社保）
  • 跨系统业务流程：北京提交自动流转上海办理（跨省通办）
  • 严格治理要求：每步留痕，审计可追溯（涉密业务）
  • 服务重用：身份认证服务被多个场景复用（办护照/驾照/银行卡共用）

SOA 三大挑战及解决方案

  • 性能（序列化开销大）→ 用 RESTful API + 缓存机制
  • 安全（传输风险）→ HTTPS + OAuth/JWT 身份认证
  • 复杂数据 → 用 SOAP + WSDL + XML Schema 处理
◆ 费曼

架构风格到底在讲什么？ 架构风格就是"盖房子的不同流派"——数据流风格像工厂流水线（原料从一头进、成品从另一头出），调用/返回像公司层级（上级调用下级、层层传递），独立构件像微信群（有人发消息、在群里注册了的人自动收到），虚拟机像翻译官（把用户说的话翻译成机器能执行的指令），数据中心像公共图书馆（所有人都去同一个地方读写数据）。C/S和B/S怎么选？ 两层像夫妻店（老板兼收银），三层像连锁餐厅（前台/后厨/仓库各司其职），B/S像外卖APP（用户用浏览器下单、不用装软件但体验差点）。SOA就是政务服务大厅——把各部门业务包装成统一窗口，你只管提交，不用管后面谁在办。

▸ 总结

五大流派各有所长——数据流流水线式处理、调用/返回层级协作、独立构件松耦合事件驱动、虚拟机规则解释执行、数据中心共享仓库推理；层次架构中三层C/S安全扩展优、B/S零客户端但交互弱；SOA 通过 WebService + ESB实现松耦合服务集成，REST 轻量高效替代传统 SOAP。
