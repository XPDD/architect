▸ 核心要点
1构件定义与在架构中的角色

定义

构件（Component）是软件系统中 可独立部署、可复用、具有明确接口和功能的模块化单元，可能是一个类、库、服务等。类比：乐高积木——每个积木有标准接口（凹凸结构），可通过组装构建复杂系统。

软件架构三大要素

软件架构 = 构件（描述） + 连接件（构件之间的相互作用） + 模式及约束（指导集成）。架构定义：系统的构件、构件的外部可见属性及相互关系。

城市类比理解

  • 软件构件 = 公安局、港口、图书馆、高铁站——每个都是子系统，内部自成体系
  • 外部可见属性 = 金融街对外提供"存款、贷款、转账"——只暴露接口，隐藏内部实现
  • 相互关系 = 地铁、公路、电网——连接方式、通信机制、依赖管理
2构件的四大核心特征
♻
可复用性
⬛
标准化接口
□
独立性
⚙
可组装性
1
可复用性
  • 设计时解耦，不依赖具体业务场景
  • 可在不同系统中重复使用
  • 如：支付模块可复用于电商、教育等系统
2
标准化接口
  • 提供明确的输入/输出接口（API或协议）
  • 隐藏内部实现细节（黑盒化）
  • 接口是构件与外界的唯一交互通道
3
独立性
  • 可独立开发、测试、部署
  • 仅通过接口与其他构件交互
  • 构件内部修改不影响外部使用者
4
可组装性
  • 支持通过配置或代码调用与其他构件组合
  • 形成完整系统功能
  • 如同乐高积木拼装成完整模型
3构件 vs 对象 — 关键区别
特性构件 Component对象 Object
部署单元独立部署单元实例单元
状态可见性无外部可见状态（黑盒）可能具有外部可见状态
复用粒度粗粒度（功能模块级别）细粒度（类/方法级别）
典型示例支付模块、用户管理组件、Docker 镜像Java 类、C++ 对象实例
设计关注点接口契约、组装方式、独立部署封装、继承、多态
4构件的组装方式（两种分类体系）

分类一：按集成方式（基于什么来组装）

组装方式技术特点适用场景典型示例
基于功能组装 通过子程序调用实现功能模块集成 传统分层架构 MVC 模式
基于数据组装 围绕核心数据结构构建框架 数据密集型系统 Jackson方法、ETL流程
面向对象组装 通过继承/多态实现复用 OOP 系统 Spring框架、Java类库

分类二：按拓扑结构（构件之间怎么连接）

1
顺序组装 🏃
  • 按顺序调用已有构件，上一个输出 = 下一个输入
  • 用两个已有构件创造新构件
  • 类比：接力赛——一棒接一棒
2
层次组装 🏢
  • 一个构件直接调用另一构件提供的服务
  • 被调用者为调用者提供服务，接口匹配兼容
  • 类比：上下级——领导派活给下属
3
叠加组装 🍽
  • 两个或以上构件放在一起创建新构件
  • 合并原构件功能，对外提供新接口
  • 原构件互不依赖，互不调用
  • 类比：拼盘菜——各菜独立摆盘，共用大盘端上桌
口诀
顺序·层次·叠加
  • 顺序 = 接力赛，数据串流
  • 层次 = 上下级，服务调用
  • 叠加 = 拼盘菜，接口合并
5组装过程中的三个关键点
I
接口匹配
  • 确保构件接口的输入/输出兼容性
  • 检查协议、数据格式一致性
  • 标准化的接口是组装的前提
C
语境适配
  • 调整构件对运行环境的依赖
  • 如数据库连接配置
  • 环境差异可能导致组装失败
E
异常处理
  • 解决组装失配问题
  • 如通信协议不一致
  • 如数据模型冲突
口诀
接口·语境·异常
  • 接口不对 → 插不进去
  • 语境不对 → 跑不起来
  • 异常不处理 → 运行时崩溃
5.1组装三种不兼容问题（通过编写适配器解决）
1
参数不兼容
  • 接口操作名相同
  • 但参数类型或个数不同
  • 例：A 调用 foo(int)，B 提供 foo(String)
2
操作不兼容
  • 提供接口和请求接口的操作名不同
  • 例：A 调用 pay()，B 只提供 makePayment()
3
操作不完备
  • 一个构件的提供接口是另一个构件请求接口的子集
  • B 提供了 5 个操作，A 只需要其中 3 个
  • 或：A 需要 5 个操作，B 只提供了 3 个
⚙
解决方案：适配器
  • 编写"胶水代码"做中间转换
  • 参数转换、操作名映射、功能补齐
  • 类似翻译官在两者之间做协调

维度CORBADCOMEJB

平台支持跨平台（Unix/Linux/Windows）主要是 Windows所有支持 Java 的平台
语言支持多语言（C++/Java/Python等）多语言（C++/VB/Java等）仅 Java

当前状态Legacy 系统维护逐步被 .NET 取代被 Spring 等轻量框架替代

各标准详解

  • EJB：三种类型——会话Bean（管理会话/业务逻辑）、实体Bean（持久化数据交互/对象映射到数据库表）、消息驱动Bean（异步消息处理）
  • DCOM：COM 的扩展，具有位置独立性和语言无关性；COM+ 是 COM 的更高层次应用，不是新版本
  • CORBA：三层结构——对象请求代理（ORB 软总线）、公共对象服务（通用工具）、公共设施（业务框架）。核心目标是解决不同平台/语言/位置的互操作问题

◆ 费曼

构件到底是什么？ 构件就是软件世界的"乐高积木"——每个积木内部很复杂（可能有齿轮、弹簧），但对外只暴露几个标准接口（凸起和凹槽）。你不用管它里面怎么造的，只要接口对上就能拼。一个系统就是一堆构件的组合。构件和对象的区别：对象是小零件（螺丝钉），构件是大模块（发动机总成）——构件没有外部可见状态（你不能从外面看到发动机内部活塞的位置），而对象可能有 getter/setter 让你直接看内部。组装构件时最怕三件事：接口不对（插不进去）、环境不对（数据库连不上）、运行时报错没处理（某个构件挂了整个系统跟着崩）。

▸ 总结

构件是架构设计的最小部署单元——具备可复用性、标准化接口、独立性和可组装性四大特征；组装方式分集成方式（功能/数据/OOP）和拓扑结构（顺序/层次/叠加）两类，不兼容时用适配器解决；三大经典标准 CORBA/DCOM/EJB 正被 RESTful/gRPC/Spring Boot/容器化等现代技术替代。
